## C03. 공개 보드와 공개본의 최소 계약

### 공개 원본과 전시물

원본 Memory/Board는 작성자의 비공개 기록으로 유지한다. 공개본은 **사용자가 확인한 내용만 읽도록 하는 경계**다. 별도 snapshot 테이블, 기존 안전한 read-model, 검증된 publication 구조 중 가장 작은 방법을 선택한다.

개념적으로 필요한 정보는 작성자, 대상 Board/Memory, 공개 필드와 이미지 revision, 공개 버전, 게시/철회 상태, 노출 위치, 관리자 차단 상태다. 이 필드를 새 테이블 여러 개로 나누는 것이 필수는 아니다.

공개 게시·미니홈 공개·팔로우 쓰기는 실제 로그인 UID를 요구한다. Guest는 사적 기록과 공개 자료 읽기를 할 수 있지만, Guest owner 문자열만으로 서버의 공개 소유권을 만들 수 없다.

### 필수 사용자 흐름

1. 공개할 보드/기억을 선택한다. 같은 작품의 카드라도 이미지·감상·날짜로 구분한다.
2. 비로그인 방문자에게 보일 제목·감상·이미지·날짜·대표 기록을 미리 보여준다. 선택하지 않은 정보는 payload에도 넣지 않는다. 집계 수·Board 이름·검색 결과도 public 범위만 사용하여 private 활동을 추론하게 하지 않는다.
3. 지원 불가·권리 미확인·이미지 미전달 항목은 이유를 표시하고 게시를 막는다. 조용히 누락한 채 '보드 전체 공개 완료'로 처리하지 않는다.
4. 명시적인 게시 행동을 수행한다. 재시도·중복 클릭에도 한 공개본만 생성한다.
5. 성공한 URL에서 실제 방문자 화면을 열 수 있다. 작성자 세션·기기·localRef에 의존하지 않는다.
6. 내용 수정은 '공개 내용 갱신'으로 확인한다. 사적인 원본 메모 편집을 자동 공개하지 않는 것을 기본안으로 한다.
7. 공개 철회·보드 비공개·삭제는 그 차이와 영향 위치를 보여준다.

Public writer는 서버에서 owner와 기대 버전, 동의 대상 hash/revision을 검증한다. preview 이후 이미지나 본문이 바뀌면 재검토를 요구한다. 클라이언트가 바꾼 `visibility`를 그대로 신뢰하지 않는다.

### 작은 상태 모델 예시

`PRIVATE → PREPARING → PUBLISHED → REVOKED`에 `FAILED`와 관리자 `HIDDEN`을 분리한다. 이름은 기존 모델에 맞출 수 있다.

준비 중 파일은 비공개 staging에 두고, 필수 자산 준비·검증이 끝난 뒤 공개한다. 실패 시 기존 공개 버전 또는 비공개 원본을 유지한다. 취소 후 오래된 성공 응답이 다시 게시되지 않도록 operation/version을 확인한다. 중단된 임시 파일은 재개/정리 정책으로 관리한다.

필수는 안정적인 공유 URL과 방문자 읽기다. 공동편집, 인기순, 새로운 공개 등급 체계, 좋아요/댓글은 필요 없다.

| 공개 권리 미확인 스크린샷·팬아트 | 해당 공개 시도만 차단·설명. 기록 자체와 승인된 다른 유형은 유지 |
| 다른 기기에 있어 현재 읽을 수 없는 local 이미지 | 표지로 몰래 바꾸지 않음. 원본 기기에서 공개 준비하거나 파일을 명시적으로 다시 제공하는 경로 |

이미지 공개를 지원한다는 것은 모든 private 이미지의 다기기 자동 백업을 지원한다는 뜻이 아니다. 공개 기능에 필요한 업로드/교체/삭제/복구만 구현한다. 현재 지원되는 Android image intake를 우선 재사용하고, Web의 입력 지원 범위는 실제 가용성과 문구를 일치시킨다.

### 입력·정리

신뢰하는 MIME 문자열뿐 아니라 실제 decode, 파일 크기/해상도 상한, 사용자별 bytes/개수, 무작위 object key/owner binding, 공개에 불필요한 EXIF·위치정보 제거, 썸네일 생성 실패, 중복·orphan 정리를 확인한다. 외부 URL을 무조건 대신 내려받는 범용 fetch 기능은 추가하지 않는다.

초기 정책은 현재 지원하는 안전한 래스터 형식을 재사용한다. SVG/HTML 등 실행성 콘텐츠를 이미지로 받아 저장소에서 그대로 서비스하지 않는다. 파일의 공개 권리 판단과 기술적 파일 검증은 별개다.

### 기존 W08/Q10의 재시도 보완 — 2026-09-25

- 잘못된 원본으로 실패한 뒤 올바른 파일을 선택하면 같은 화면에서 정상 재시도가 가능해야 한다. 취소 후 재시도도 실패한 예약에 영구 고정되지 않는다.
- 실패가 확정된 작업과 완료 응답만 유실된 작업을 구분한다. 후자는 원래 operation의 서버 상태를 먼저 확인하여 중복 파일·중복 비용·기완료 파일 삭제를 피한다.
- 병렬 클릭·취소·소유자 또는 sourceVersion 변경·quota 거절 뒤에도 원본·public state·예약량·파일 참조가 계약대로 남아야 한다. 매 요청마다 무조건 새 ID를 만드는 것은 해결이 아니다.
- 현재 신뢰된 이미지 승인 레코드와 policy revision을 만족하는 실제 처리 경로를 D04/W14에서 확인한다. 사용자 체크박스만으로 신뢰된 승인을 생성하거나 검사를 제거하지 않는다.
- 이 항목은 기존 C04의 실패 복구 계약을 구체화한다. 신규 업로드 플랫폼이나 새로운 권리 제한을 추가하는 것이 아니다.

### 반드시 구분할 세 가지

- public bucket의 파일은 공개 URL로 접근 가능하다. private 원본이나 공개 전 staging을 그런 버킷에 놓고 UI만 숨기는 것은 허용하지 않는다. [W2]
- private bucket의 signed URL은 시간 제한 접근 경로다. 이미 발급된 URL이 Auth 키 변경만으로 무효화된다고 가정하지 않는다. [W2]
- 비로그인 방문자의 공개 열람과, 사용자 이미지 bytes가 영구 무인증 URL에 노출되는 것은 같은 설계가 아니다.

**기본안:** 철회가 필요한 사용자 공개 이미지에는 서버가 현재 공개 상태를 확인하는 전달 경계를 사용한다. 가능한 경우 `no-store`와 재검증을 적용한다. 인증이 없는 방문자 요청이어도 서버가 publication의 유효성을 판정할 수 있다. client에 privileged key를 보내지 않는다. [W3]

다른 전달 방법을 선택하면 철회 후 페이지/JSON/thumbnail/original/OG preview/CDN/service worker에서 각각 얼마 동안 남을 수 있는지를 D05에 기록·승인받는다. URL을 랜덤하게 만드는 것만으로 접근 통제나 철회를 달성했다고 하지 않는다.

최초 배포의 신규 요청은 최신 철회 상태를 확인한다는 기본 계약을 우선한다. 더 긴 캐시·서명 URL 유효기간을 택하면 그 허용 지연을 실제로 측정하고 고지한다. 이미 다운로드한 외부 사본·오프라인 캡처는 회수 보장 대상이 아니다.

초기 링크 preview는 일반 브랜드 이미지로 제공해도 된다. 공개 이미지가 포함된 사용자별 OG 카드를 새로 생성하는 기능은 필수가 아니다. 이미 사용 중이면 철회 검증 범위에 포함한다.

## C05. 여러 공개 위치·수정·삭제·차단의 의미

### 공개 노출 기본안

카드의 공개 표현이 유효하고 작성자·카드가 차단되지 않았으며, 현재 활성 공개 보드 또는 미니홈 전시 참조가 하나 이상 있을 때만 방문자에게 그 표현을 제공한다. 내부 구현은 기존 구조를 활용하되 아래 결과가 같아야 한다.

| 행동 | 결과 |
|---|---|
| private Board에 카드 추가 | 원본 이동/복사/공개 없음 |
| 공개 Board의 초안에 private 카드 추가 | 자동 공개 없음. 공개 대상 재검토와 갱신 필요 |
| Board 하나를 비공개 전환 | 그 Board의 공개 주소·참조는 철회. 다른 명시적 공개 위치는 남을 수 있음을 미리 표시 |
| 카드의 '모든 곳에서 공개 중지' | 연결된 공개 보드·미니홈·공개 카드 경로 모두 차단. private 원본 유지 |
| 원본 Memory 삭제 | 연관된 공개 표현 즉시 접근 철회, 보드 관계 정리. 공용 표지 원본과 다른 사용자 자료는 유지 |
| 미니홈 비공개 | 미니홈의 노출과 그 전시 참조 철회. 별도 공개 Board가 있으면 남는 범위를 안내 |
| 게시 후 private 감상 수정 | 공개본 자동 갱신 없음이 기본. '공개본과 다름' 상태에서 재검토 후 갱신 |
| 관리자 임시 비공개 | 일반 사용자 재게시·다른 보드 연결·이전 client 재시도로 우회할 수 없음 |
| 계정 정지/삭제 | 승인된 범위의 공개물/팔로우/업로드에 서버 제한. shared catalog 원본은 영향 없음 |

기존 구현이 다른 노출 모델을 사용하면 작업을 무조건 갈아엎지 않는다. M2 W07에서 차이를 기록하고 사용자가 이해할 수 있는 동일한 철회·노출 통제를 확보한다. '보드 비공개'와 '내 모든 기록 비공개'를 같은 이름으로 쓰지 않는다.

동시 게시/철회/원본 삭제, 다른 기기의 예전 요청, 관리자 차단 이후 재업로드, 복원한 DB의 오래된 공개 상태를 모두 검증한다. 철회 사실을 지워서 재시도와 복원으로 공개가 부활하게 만들지 않는다.

비회원에게 존재 여부가 민감한 private/삭제/차단 대상은 불필요하게 구분해 알려주지 않아도 된다. 소유자와 관리자에게는 필요한 원인·다음 행동을 별도로 안내한다. 일반 네트워크 오류를 '기록 없음'으로 위장하지 않는다.

## C06. 공개 미니홈 — 전시물과 사람을 연결하는 최소 화면

필수: 공개 닉네임, 선택적 소개, 사용자가 고른 대표 공개 기억/보드, 작성자 식별, 공유 URL, 공개/비공개 상태, 방문자 미리보기. 연락처·이메일·계정 ID·private 취향 원문을 자동 전시하지 않는다.

대표 기록의 수동 선택·순서 조절 정도로 시작한다. 복잡한 블록 편집기·테마 상점·3D 미니홈은 만들지 않는다. 실제 공개 가능한 자료만 표시하며, 철회된 카드는 blank 개인 이미지 대신 안전하게 제거/가림 처리한다.

이미지·본문은 모바일에서 실제로 읽을 수 있어야 한다. 닉네임만 보이는 빈 프로필로 전시 기능을 완료하지 않는다. 새 이용자는 공개 기록이 없다는 안내와 소유자용 다음 행동을 본다. 방문자에게 private 기록 만들기나 관리자 메뉴가 노출되지 않게 한다.

공유 URL은 가능하면 기존 안정 식별자를 재사용한다. 이름 변경 때문에 깨지지 않게 하되 새로운 사용자명 예약 시스템을 필수로 만들지 않는다. 사용자 입력은 HTML/script로 실행되지 않게 처리한다.

**W13 연결 보완:** 공유 보드에 공개된 작성자 미니홈이 있으면 안전한 공개 식별자/닉네임으로 방문 경로를 제공한다. 민감한 Auth 식별자·이메일·private profile을 공개 DTO에 섞지 않는다. 홈이 없거나 비공개·가림·철회되면 안전하게 생략하고, 작성자는 연결 공개의 의미를 확인할 수 있어야 한다. 로그인·팔로우는 원래 공개 문맥으로 돌아오며 자동 팔로우하지 않는다. 이 경로를 제품상 제외하려면 미니홈 공유를 기본 진입점으로 바꾸는 명시 결정이 필요하고, 단순히 기능을 빠뜨린 상태를 완료로 처리하지 않는다.

## C07. 팔로우·재방문·차단

- 팔로우는 private 자료 열람 권한을 부여하지 않는다.
- 본인 팔로우 금지, 중복 클릭/재시도에서 관계 1개, 해제는 안전하게 반복 실행 가능.
- B는 '내가 팔로우한 사람' 목록에서 A의 미니홈으로 다시 이동한다. 팔로워 숫자만 변하는 버튼은 완료가 아니다. 내 관계 목록을 모든 방문자에게 공개하는 기능은 첫 출시 필수가 아니며, 별도 승인 없이 전체 관계 그래프를 노출하지 않는다.
- 비회원은 공개 내용을 볼 수 있다. 팔로우 요청은 로그인으로 연결하고 원래 안전한 내부 주소로 복귀한다. 로그인 성공만으로 동의 없이 여러 계정을 자동 팔로우하지 않는다.
- 삭제·정지·공개하지 않은 미니홈의 목록 표현과 다음 행동을 정의한다. 다른 사람의 비공개 상태 이유를 누설하지 않는다.
- 사용자는 차단/해제를 할 수 있다. 기본안은 기존 양방향 팔로우 제거, 새 팔로우 금지, 내 관계 목록의 노출 억제다. 차단 해제 후 팔로우를 자동 복구하지 않는다.
- **로그인 차단이 공개 자료의 비회원 열람까지 막는다고 약속하지 않는다.** 공개 자체를 끄는 것은 작성자의 별도 공개 철회다.
- 차단된 이용자도 안전 문제를 신고하는 통로까지 봉쇄하지 않는다. 악성 신고는 관리자와 rate limit으로 대응한다.

기본 탐색 경로는 공유 링크→미니홈→팔로우→내 목록이다. 추천 알고리즘·뉴스피드·푸시 알림·DM은 없더라도 이 계약을 만족할 수 있다.

## C08. 신고·관리자 조치·지원

필수 흐름은 공개 대상에서 신고→접수 확인→운영자 검토→유지/임시 비공개/복원/계정 제한→사유 통지→이의제기 접수→감사 이력이다. 사용자에게 접수 수단은 보여야 한다. 운영자 측 화면은 검증된 제한 명령/기존 dashboard로 시작할 수 있다.

### 최소 운영 계약

| 기능 | 최소 구현/검증 |
|---|---|
| 신고 | 대상 public ID·분류·신고시각·선택 설명, 중복/남용 제한. 외부 문의도 같은 처리 목록에 연결 |
| 임시 비공개/복원 | 서버 reader와 이미지 경계에 반영, 사유/작업자/대상/version 기록 |
| 통지·이의제기 | 실제 작동하는 인앱 또는 운영 메일 채널 1개, 담당자와 처리 상태 |
| 계정 제한 | 게시·업로드·팔로우 제한을 필요한 수준으로 분리. 지원/내보내기/삭제 요청 보장 범위 명시 |
| 관리자 권한 | 일반 계정/client metadata로 승격 불가, 실제 역할 테스트, 필요한 권한만 부여 |
| 긴급 중지 | 게시/업로드 쓰기와 공개 읽기의 중지 범위를 구분, 버튼 flag뿐 아니라 서버에 적용 |
| 감사 | 누가·무엇을·왜·어떤 상태에서 바꿨는지. private 원문을 기본 로그에 보관하지 않음 |

기본 운영 대상은 공개된 자료와 신고 사건이다. private 원본을 모든 관리자가 상시 탐색하는 기능은 만들지 않는다. 신고 자체로 무조건 자동 삭제하거나 자동 공개 확대하지 않는다. 복구는 해당 공개 동의와 차단 상태를 다시 확인한다.

운영자도 조치의 취소/복원 경로를 실제로 실행해야 한다. 문서에 절차만 쓰고 수행 권한이나 연락처가 없는 것은 완료가 아니다. 신고·공개 원본 보존 기간과 증거 접근은 D04/D05에서 정한다.

## C09. 한도·비용·실패 처리

실제 요청 경계별로 동기화 쓰기, publish/revoke, image upload, follow/report, 익명 공개 page/image read, catalog read를 나눈다. Guest 로컬 작성에 서버 quota를 적용하지 않는다.

사용자별 제한은 인증된 서버 ID를 기준으로 하고, 병렬 실행과 재시도에 안전해야 한다. frontend disabled는 보안 통제가 아니다. 기존 직통 REST/RPC/Storage 경로가 남아 있으면 그 경로도 검증한다.

숫자는 D03에서 승인한다. 초기 정상 여정·Guest 승격·신규 기기 sync·공개 이미지 게시의 호출 수/bytes/지연을 측정하고 여유를 둔다. 50/200 batch 크기나 5,000 resync 경계를 사용자 상품 한도로 그대로 쓰지 않는다.

quota에 막혀도 자기 기록의 삭제/공개 철회/내보내기와 정상 지원 경로가 함께 막히지 않도록 한다. 오래된 토큰, 두 기기, 중복 operation, 초과 뒤 재시도, 제한 해제·만료 있는 임시 override를 시험한다.

익명 공개 열람에 엄격한 개인별 quota를 보장한다고 하지 않는다. 페이지 상한·응답 크기·cache·전역 예산/경보/중지 등 실제 달성하는 통제를 문구에 반영한다. 더 강한 보호가 필요하면 직통 우회까지 포함한 경계로 해결한다.

## C10. 카탈로그 갱신·복구·배포

### 카탈로그

기존 collector/validator/exporter를 재사용해 **후보 수집→diff→검증→운영 승인→STAGING→게시→health→복구**를 연결한다. 자동 게시보다 후보 생성·검사 자동화를 먼저 한다. 초기 수동 실행도 담당·주기·재개·실제 리허설이 있으면 최소 기능으로 허용하되, 정기 health와 실행 누락 경보는 작동해야 한다.

새 시즌을 이름만으로 병합하지 않는다. stable ID·기존 카드의 cover revision·공개 전시 참조를 보존한다. 실패/429/no-op 재실행/동시 게시에서 기존 정상 ACTIVE를 손상시키지 않는다. S08/S09는 같은 게시/복구 계약으로 마감한다.

### 복구 대상

로컬 기록 백업, 계정 DB, 사용자 공개 이미지 bytes, 공용 cover bytes, 외부 canonical·checkpoint·release artifact를 구분한다. DB 백업에 Storage 객체 본문이 들어 있다고 가정하지 않는다. [W4]

지원하지 않는 private 이미지 backup이나 비어 있지 않은 계정 병합을 약속하지 않는다. 공개용 이미지 저장소는 신규 복구 책임에 포함된다. 원본 기기 사진까지 원격 복원했다고 하지 않는다.

### 배포

승인된 Git production 경로를 유지한다. 필요한 checks가 실패하면 배포/승격이 실제로 막혀야 한다. 정확한 commit, migration, catalog release, public flags, 운영 도메인의 build-info를 대조한다. 의존성 교체나 CLI 직접 배포로 우회하지 않는다.

SW는 build-info·권한/계정 응답·철회 관련 자료와 immutable asset을 구분한다. 계정 전환 시 private cache를 섞지 않으며, 이전 SW에서 업데이트·롤백이 동작해야 한다. 404/500 응답을 정상 자산으로 영구 캐시하지 않는다.

code rollback과 데이터/공개 상태 복원은 다르다. 복원 뒤 최신 철회/차단 상태가 확인되기 전 Public을 열지 않는다.

## C11. 모든 노출 화면과 버튼의 UX 계약

### 조사 단위

M0/M5에서 현재 route·역할·feature flag·상태별 노출 기능을 확인한다. 과거 '15 route/356 요소'는 과거 관측값이지 현재 전수 검증 개수가 아니다.

각 action은 `화면/역할 → label → 실제 handler/API → 성공 상태/목적지 → 취소/실패 → 복귀/초점`으로 연결한다. 동적 목록의 동일 버튼을 수백 개 별도 티켓으로 만들지 않고, 같은 계약의 인스턴스로 테스트한다. 공유 URL·숨긴 관리자 URL·legacy direct route도 접근 제어 대상이다.

`완료 / 현재 계약 수정 필요 / 의도적 비활성(사유·서버 차단) / 미검증` 중 하나를 기록한다. 클릭 가능한 외형의 무반응 항목과 fake success는 남기지 않는다. 미검증은 완료가 아니다.
