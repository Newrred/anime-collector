# MOEMOA · 개인 운영자를 위한 최소 운영 계약

2026-09-25 · 새 관리자 플랫폼 설계가 아니다. 기존 운영 명령·대시보드에 필요한 조회와 조치만 연결한다. 지금 서비스에 모두 배치되어 있다는 의미가 아니다.

## 1. 운영자가 평소 볼 것은 한 장의 요약이다

하루 2~3회 다음을 확인할 수 있는 **기존 status 출력 또는 얇은 관리자 요약**을 권장한다. 먼저 기존 도구의 같은 정보가 있는지 확인하고 부족한 항목만 추가한다.

| 영역 | 기본 표시 | 문제가 있을 때 연결 |
|---|---|---|
| 운영 상태 | build SHA, 활성 정책 revision, catalog release, 최근 성공 시각 | 해당 변경/실패 원인 |
| 월 추가비 | 이번 청구기간 고정비 예상, 변동비 추정, 지연 중인 공급자 집계, 월말 예상, 안전 여유 | 신규 접수/공개 전송 제한 상태 |
| 이미지 | 사용자 논리량, 실제 private/public/staging/retired bytes, 예약 만료, quota 실패 | 재정산·안전 청소 결과 |
| 이용자 처리 | 신고·이의·삭제 요청·오래된 처리 대기 수 | 기존 조치 도구·접수 채널 |
| 연동·복구 | 이미지/메타데이터 실패와 pending, 자동 사본·health·후보수집 마지막 성공 | 실패 run 및 재시도/지원 |

화면에 비공개 감상 원문·개인 이미지·토큰·이메일을 기본으로 나열하지 않는다. 사용자 지원은 불투명 ID·건수·상태부터 확인한다. 신고된 공개 자료는 권한 범위에서 검토하되, 비공개 사진 전체를 수동 심사할 콘솔은 만들지 않는다.

운영자 정보는 기존 자료의 sinong 및 제공된 지원 연락처를 재확인해 사용한다. 비밀값·접속정보는 문서/공개 Git에 넣지 않는다. 이 문서 작성 과정에서는 실제 청구서·대시보드를 조회하지 않았다.

## 2. 설정은 ‘기준 파일 하나 + 서버 활성 revision’으로 관리

1. `service-policy.candidate.json`과 schema는 변경 후보·검토의 기준이다. 앱이 패키지를 읽었다고 운영에 적용되지 않는다.
2. 검토 후 기존 서버 운영 정책에 mapping한다. 실제 읽기/쓰기 제한의 권위는 **서버 활성 revision**이다.
3. 클라이언트는 허용된 공개 부분만 읽어 용량·형식·지원 상태를 표시한다. 사용자 metadata의 plan/role/bytes를 신뢰하지 않는다.
4. 과거 revision과 변경 사유는 감사 기록으로 남기되 **별도 진행판은 만들지 않는다**. 현재 개발 상태는 release-v2 진행판에만 기록한다.
5. 모든 설정 변경에 expectedRevision 또는 동일한 compare-and-swap 검사를 사용한다. 동시에 두 변경이 덮어쓰지 않아야 한다.
6. 운영자가 한도 변경·만료 있는 예외·일시중지·복구를 할 수 있게 한다. 처음에는 검증된 명령/RPC이면 충분하고, 사용이 반복되어 불편한 부분만 얇은 UI로 감싼다.

### 설정 변경 순서

`후보 편집 → 구조/일관성 검사 → 이전값과 영향 미리보기 → D03/D04/D05 관련 승인 → 격리 테스트 → 운영 적용 승인 → 서버 revision 전환 → 표본 확인 → 이력 기록`

작은 용량 변경 때 매번 migration을 만들지 않는다. 저장 구조나 권한 자체가 바뀔 때만 기존 migration 절차를 따른다. 운영값/비밀값/feature gate는 서로 다르며, 정책이 승인됐다고 Public 자동 활성화가 승인된 것은 아니다.

### 오류·되돌리기

- 알 수 없는 revision·잘못된 설정·필수 미정값이면 새 원격 이미지 쓰기를 열지 않는다. 기존 정상 정책으로 제한 운영할 수 있는지 확인한다.
- 용량을 낮춰도 이미 저장한 파일을 자동으로 삭제하지 않는다. 현 사용량과 추가 가능 여부를 명확하게 표시한다.
- 정책 롤백이 삭제/철회/제재를 되살리면 안 된다. 데이터 상태와 접근 금지 이력은 별도로 보존한다.
- 예외는 사용자·허용량·만료·이유·실행자 단위로 설정한다. 영구 무제한 예외, 클라이언트에서 직접 plan 변경, 무료를 유료로 자동 전환은 금지한다.
- 작은 한도를 반복해서 지웠다 올리며 이용량을 초기화하지 않도록 사용량과 limit 변경을 분리한다.

## 3. 비용 관리 — 추가 월 50,000원

**포함:** MOEMOA 때문에 추가되는 DB·Storage·함수·전송·추가 프로젝트·메일/관측·사본·결제 환전/세금. **제외:** 도메인, 서비스 홍보 광고비, 다른 프로젝트 때문에 이미 내는 Vercel 기본료. MOEMOA가 일으킨 Vercel 초과료는 포함한다. 광고/구독 수익을 가정하여 예산을 늘리지 않는다.

기존 다른 프로젝트들의 공유 포함량과 청구 방식을 확인하고, MOEMOA 사용량을 서비스·요청 경로별로 귀속한다. 공급자 청구를 완전히 나눌 수 없는 항목은 보수적으로 예상하고 구분이 불가능하다고 기록한다.

### 경고 기준은 고정비를 뺀 뒤 계산한다

```text
변동비 안전 예산 = 50,000원 - 이번 달 고정비 예상 - 안전 여유
관측할 값 = 변동비 추정 + 이미 승인된 요청/작업의 잔여 예상 + 미반영 사용량 여유
```

시작 후보: 안전 여유5,000원. 남은 변동비 예산의 70%에서 경고, 90%에서 감속, 100%에서 추가 고비용 작업 제한. 비율은 운영값이며 D03에서 수정할 수 있다. 월말 예상이 초과하는 경우 지금 청구액이 작더라도 먼저 조치한다.

예를 들어 고정비40,000원·여유5,000원이라면 안전 변동비는5,000원이다. 70%경고는 총43,500원 수준, 추가비 제한은45,000원 수준이다. **실제 고정비를 확인한 계산이 아니라 원리를 설명한 예시**다. 기본료가 이미42,000원인데30,000원 경고로 모든 신규 사용을 막는 설정을 사용하지 않는다.

변동비 안전 예산이0 이하라면 정식 서비스 수용량을 증액 없이 보장할 수 없다. 데이터 기능을 삭제하기 전에 실제 청구/불필요 추가 프로젝트/옵션을 확인하고, 해결되지 않으면 D03 차단으로 기록한다.

### 상태별 자동 대응 제안

| 상태 | 자동 또는 즉시 가능한 최소 대응 | 보존할 것 |
|---|---|---|
| NORMAL | 정상 한도 적용 | 모든 지원 기능 |
| WARNING | 담당자 경보·관측 시각·월말 예상 표시 | 불필요한 사용자 차단 없음 |
| THROTTLED | 신규 이미지 동시성·속도 축소, 신규가입/공개접수 상한 검토 | 기존 기록과 pending |
| NEW_WRITES_PAUSED | 새 고비용 이미지 쓰기·신규 공개 준비 제한, 이미 시작한 작업 안전 정리 | 텍스트·기존읽기·정리·지원 가능한 범위 |
| PUBLIC_MEDIA_PAUSED | 공개 이미지 전송을 우선 일시 제한, 유지 가능한 텍스트 안내 | private 자료가 공개되지 않음; 파일 삭제 없음 |
| COST_TELEMETRY_STALE | 마지막 확인 시각 표시, 로컬 사용·알려진 안전 한도 유지. 새 고비용 승인 보수적으로 차단 | 모르는 사용량을0으로 계산하지 않음 |

비공개 대량 다운로드도 비용이다. 자기 자료 읽기·내보내기를 무제한 면제로 만들지 말고 별도 회복/지원 예산으로 속도를 제한한다. 제한으로 자기 자료를 영구적으로 돌려받을 수 없게 하거나 결제를 강요하지 않는다. 큰 ZIP 일괄 내보내기는 이번 필수가 아니며, 계정 manifest와 페이지별/순차적인 **최적화 사본 다운로드**로 지원 범위를 충족시킬 수 있다.

개별 전송 카운터의 월 기준은 후보 설정상 UTC 달력월이며, UI에는 사용자 시간대로 다음 초기화 시점을 보여준다. 공급자의 청구기간이 다르면 따로 집계한다. 저장50MB는 월간 초기화 항목이 아니다. 재시도는 논리 보유량을 중복 차감하지 않지만 요청 폭주·연산 예산에서는 검사한다.

경보는 요금 hard cap이 아니다. 공급자 집계 지연·환율·세금·공유 팀 사용량 때문에 정확한 원화 상한을 API 설정 하나로 보장할 수 없다. 사전 여유·서버 제한·직접 경로 검사·공급자 옵션을 함께 사용한다. Supabase Spend Cap도 일부 항목만 포함하며 컴퓨팅 등은 별도다. [WEB6]

다른 프로젝트까지 정지하는 Vercel 팀 전체 자동중단을 무심코 적용하지 않는다. MOEMOA 경계에서 대응한다. 보안·제재·비용 제한은 서로 다른 사유로 기록하고, 비용 기간 초기화/정책 롤백이 보안 정지를 풀지 못하게 한다.

## 4. 최소 관리자 동작 — 기존 기능 재사용 우선

아래 이름은 **논리 동작명이며 현재 실행 가능한 CLI 명령이라고 주장하지 않는다.** Codex가 기존 RPC/도구에 연결하고 실제 실행법만 최종 인수 문서에 적는다.

| 논리 동작 | 필요한 입력·보호 |
|---|---|
| 상태/정책/사용량 조회 | 범위·revision·관측 시각. 원문 private 내용 제외 |
| 정책 검증·차이 미리보기 | 후보hash, 예상 이전revision, 영향 계정수·용량(집계) |
| 승인 정책 적용·rollback | 운영권한·expectedRevision·이유·승인근거 |
| 사용자 임시 한도 예외 | target, 만료, 용량/속도, 이유. 자기 원문 조회는 별도 권한 |
| 이미지 쓰기/공개 전송 일시중지·재개 | 대상 기능·원인·정책. 읽기와 삭제까지 무차별 중단 금지 |
| 신고 가림/복원·계정 제한 | 신고·사유·통지·감사. 작성자 철회를 관리자 복원이 무효화하지 않음 |
| 예약·사용량 대조/안전 청소 | 기본 dry-run. 활성작업·참조·삭제이력 확인 후 승인 범위만 |
| 백업·복구 상태 확인 | 사본 위치의 접근권한·hash·마지막성공·실패/미실행 |

일반 사용자 화면에는 하나의 **저장공간 관리** 영역만 우선 추가한다: 사용량·한도·연동 pending·최근 오류·큰 이미지 식별·삭제 영향·최적화 사본 받기. 따로 파일 관리자/폴더/드라이브를 만들지 않는다. 이미 있는 DataCenter/Memory 상세/Archive 선택 기능을 재사용한다.

## 5. 하루 운영과 긴급 상황

정기 확인은2~3회로 계획한다. 매회 비용·서비스/연동 실패·신고/삭제 대기·자동작업 마지막성공을 요약해서 보고, 담당 조치가 있을 때만 세부 화면에 들어간다. 주간에는 용량 추세·예외 만료·카탈로그 후보·백업 상태를 확인한다.

이 빈도는24시간 긴급 대응 약속이 아니다. 긴급 공개 노출·권한 사고·비용 급증은 즉시 경보와 해당 기능 일시중지를 제공하고, 대응 불가 기간에는 신규 공개/이미지 접수를 제한하거나 대체 담당자를 정한다. 일반 신고 처리 기한·공개 이미지 허용범위·국가·연령은 D04 승인값을 사용한다.

| 사고 | 최초 조치 | 복구·종료 |
|---|---|---|
| 타인의 private 이미지 접근 | 관련 media 읽기/쓰기 좁게 중지, 범위 조사·로그보존 | 권한 수정·A/B/익명 직접요청 통과 후 승인 재개 |
| 이미지 준비 실패 반복 | 새 준비 감속, 오류코드·미완료 예약 조회 | 동일 작업 완료 여부 확인 후 재시도/정리 |
| 원격 저장 장애 | 로컬 결과·pending 보존, ‘연동 대기’ 표시 | 재전송 중복0·다른기기 실제보기 후 정상화 |
| 갑작스런 전송 급증 | 비정상 방문·직통 경로·공개 미디어를 제한 | 정상 사용과 분리, 수치 재검토 후 승인 재개 |
| 삭제/철회 반영 실패 | 해당 공개 읽기 차단부터, 참조/캐시 점검 | 기존 공개URL·snapshot·미니홈·사본 비노출 확인 |
| 심사 대기 과부하 | 신규 공개 이미지 접수만 제한 | 자동 영구삭제·단순 신고수 기반 무조건삭제 금지 |

신고/권리 검토와 비공개 이미지 저장 허용은 다른 정책이다. 비공개 이미지 연동을 열기 위해 모든 사용자가 파일마다 공개 승인 심사를 통과하게 만들지 않는다. 기존 신뢰된 공개 승인 레코드를 없애지도 않는다.

## 6. 보존·백업·삭제

- 사용자 원본은 기기 책임이지만, 서버 최적화 사본·manifest·quota 상태·계정 관계는 서비스 복구 범위다.
- DB사본, **실제 object bytes**, 카탈로그 원본/표지revision, 최신 삭제·철회·제재 journal은 나누어 보관한다. DB백업이 object 파일을 포함한다고 설명하지 않는다. [WEB7]
- RPO/RTO/보존일/파일 purge 지연은 D05에서 확정한다. 샘플 null을 자동7일/영구보관으로 해석하지 않는다.
- 청소 job은 실행 성공뿐 아니라 실행되지 않은 상태도 감지한다. 만료예약을 정리할 때 active lease·READY 결과·참조·불확실한 commit을 먼저 검사한다.
- 사용자 삭제 후 논리 quota 반환과 실제 파일 purge 완료는 구분한다. 불확실한 실패에서 둘 다 다시 차감하거나0으로 맞추지 않는다.
- 오래된 backup 복원 시 **최신 철회/삭제/제재 fence 적용 전에 Public을 열지 않는다.** private 권한·계정삭제도 다시 점검한다.
- 새 이미지 경로의 실제 사본 왕복만 추가 검증한다. 새 실패 없이 기존72table복원 도구를 다시 만들지 않는다.
- 지원 export는 메타데이터 JSON과 연동된 최적화 사본의 범위를 정확히 적는다. 개인 원본도 복구된다고 표시하지 않는다.

## 8. 운영자가 마감 시 채울 최소 값 — 기존 D03~D05에서만 관리

- D03: 실제 고정비/추가비 범위, 남은 예산, 무료 전송·전역 보유/전송·수용 규모, 실제 경보 수신, 알려진 집계 지연, 기능 중단 실행 근거.
- D04: 최종 지원 국가·연령·콘텐츠·연동/공개 설명, 문의·신고·권리·삭제 책임자, 긴급 대응 범위. 과거19+ 제안 등을 승인 사실로 바꾸지 않는다.
- D05: metadata/최적화 사본·표지·canonical·철회 journal 사본 위치, 보존일/복구목표/purge·철회 지연, 내보내기 범위.

앱 구현을 마감해도 이 값과 실제 환경 검증이 없으면 운영 적용은 대기한다. 대기 시간을 다른 신규 기능 개발로 채우지 않는다.
