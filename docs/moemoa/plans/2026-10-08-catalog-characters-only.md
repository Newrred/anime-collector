# 카탈로그 캐릭터 단일 조회 ExecPlan

## 1. 목적과 사용자 결과
작품 화면과 캐릭터 선택 화면이 AniList를 브라우저에서 직접 조회하지 않고 MOEMOA 카탈로그의 캐릭터만 사용한다. 누락 작품은 출처·작품 ID를 검증한 별도 데이터 릴리스로 보강한다.

## 2. 관련 확정 결정
`ANILIST-PROD-01`은 AniList Production 보강을 사용자 확인 권한으로 기록하고, 정확한 작품 연결과 필드 검토를 요구한다. 외부 ID는 내부 작품 ID를 대체하지 않는다. 운영 DB 릴리스는 버전 관리된 코드·데이터 릴리스 ID·복구 경로를 요구한다.

## 3. 현재 상태와 저장소 증거
`titleCharacters.js`는 카탈로그 결과가 비거나 실패하면 AniList를 직접 읽는다. `TitleFavoriteCharacters.jsx`는 카탈로그를 명시적으로 끄고 AniList만 읽는다. `catalogRepository.js`는 `catalog_anime_people`을 조회한다. 2026-10-08 운영 카탈로그 익명 읽기 감사: 작품 4,292개, 첫 캐릭터 페이지가 있는 작품 4,047개, 없는 작품 245개. 누락 245개 중 199개는 AniList ID가 있고 46개는 없다. 131개는 2026-09-08 추가 배치이며 당시 캐릭터가 `NOT_FETCHED`였다.

## 4. 범위
### 포함
- 화면의 AniList 직접 대체 조회 제거, 카탈로그 조회 실패와 빈 데이터 구분.
- 즐겨찾기 후보도 내부 작품 ID로 카탈로그 조회.
- 누락 범위의 재현 가능한 읽기 전용 감사와 보강 후보 준비.
### 제외
- 기존 캐릭터 즐겨찾기·기록의 삭제 또는 임의 ID 변경.
- 검토 없는 외부 작품 자동 병합, 운영 활성화 또는 광범위 재수집.

## 5. 아키텍처·데이터 흐름
AniList는 허용 범위의 오프라인 수집·검토 단계에서만 원천 자료로 사용한다. 검토된 `CanonicalAnime`의 캐릭터가 `ServiceProjection`과 `catalog_anime_people`을 거쳐 앱에 제공된다. 앱은 AniList에 직접 요청하지 않는다.

## 6. 변경 파일 지도
`src/features/titles/application/titleCharacters.js`, `TitleFavoriteCharacters.jsx`, `TitleHub.jsx`, 관련 단위 테스트, 본 계획. 데이터 보강 도구·릴리스 증거는 별도 진행 기록에 명시한다.

## 7. 데이터·스키마 마이그레이션
스키마 변경 없음. 운영 데이터는 기존 active release를 보존한 새 staging release를 준비하고, 검증 뒤 명시적 승인 하에 전환한다. 46개 미연결 작품은 자동 매칭하지 않는다.

## 8. 마일스톤
1. 운영/로컬 데이터 누락 범위를 대조하고 ID·권리 상태를 기록한다.
2. 앱 조회를 카탈로그 단일 경로로 바꾸고 기존 정상 작품/빈 작품/오류/페이지 검사를 통과한다.
3. 누락 199개 중 정확히 연결된 자료의 보강 후보를 만들고 충돌·출처·해시를 검증한다.
4. 데이터 staging 전체 비교, 운영 승인, 활성화와 복구 확인을 별도 단계로 수행한다.

## 9. 테스트와 검증
단위 테스트, Web build, 카탈로그 row 해시·작품 ID 대조, 활성 릴리스 전후의 캐릭터 페이지 수와 기존 row 불변성 확인.

## 10. 보안·개인정보·권리 영향
브라우저의 AniList 직접 호출이 사라진다. 새 수집은 `ANILIST-PROD-01`의 사용자 확인 허가와 최신 공식 약관의 적용 범위를 재확인하며, 요청 제한·403/429를 준수한다. 비밀 키와 원문 자료는 Git에 넣지 않는다.

## 11. 관찰 가능성·분석 이벤트
캐릭터가 없는 작품 수와 조회 실패를 분리한다. 사용자 검색어·개인 기록은 로그에 남기지 않는다.

## 12. 롤백·복구
앱 코드는 이전 Git SHA로 되돌린다. 데이터는 이전 active release를 재활성화한다. 기존 캐릭터·즐겨찾기는 삭제하지 않는다.

## 13. 위험과 완화
없는 캐릭터를 빈 결과로 보여주는 공백은 보강 완료 전까지 남는다. 작품 ID 없는 46개는 검토 큐로 분리한다. AniList 약관과 기존 사용자 보유 허가의 차이는 운영 수집 전에 확인한다.

## 14. 필요한 사용자 결정
저장소의 `ANILIST-PROD-01`은 캐릭터를 포함한 Production 보강을 사용자 확인 허가 범위로 기록한다. 새로운 권한을 추정해 확대하지 않는다. 검토 결과와 릴리스 ID를 제시한 뒤 운영 DB 릴리스의 staging·활성화 승인을 받는다. ID가 없는 46개는 별도 작품 연결 검토가 필요하다.

## 15. 진행 기록
- 2026-10-08: 관련 코드·권리 기록·운영 카탈로그를 대조하고 245개 누락을 확인했다.
- 2026-10-08: 운영 active `catalog-add-7e982253b551b92984460a5e`의 4,292개 작품과 5,028개 캐릭터 페이지를 읽기 전용으로 보존했다. AniList ID가 고유하게 연결된 199개를 기존 Registry 간격·요청 제한에 맞춰 수집했다. 131개에는 캐릭터 3,644명 중 유효한 목록이 있었고 68개는 AniList에도 캐릭터가 0명이었다.
- 2026-10-08: 후보 `catalog-people-b05fefa545fcce9864eb476f` 생성. 131개 작품의 상세 캐릭터 수와 새 페이지 186개만 바뀌며 총 페이지 5,214개가 된다. 기존 4,161개 작품 행, 전체 작품 검색·표지 행, 기존 캐릭터 페이지는 release_id 이외 동일함을 해시로 검증했다. 운영 staging·활성화는 하지 않았다.
- 2026-10-08: 사용자 승인 후 후보를 운영 DB에 staging, 네 테이블의 전수 행 해시를 확인하고 활성화했다. 운영 DB에 최신 조건부 전환 함수가 없어 기존 전환 함수를 사용했다. 익명 읽기 재감사에서 4,178개 작품이 캐릭터를 표시하고 114개는 빈 결과였다. 46개 미바인딩 작품은 그대로 보류한다.

## 16. 발견 사항과 계획 변경
- 최신 공식 AniList 약관은 대량 수집과 API를 저장소 대용으로 쓰는 행위를 제한한다. 저장소에는 사용자가 별도로 확보했다고 확인한 Production 허가만 기록돼 있고 원문은 없다. 이번 수집은 고유 작품 ID가 이미 연결된 누락 199개만 대상으로 제한한다.

## 17. 완료 보고
화면의 캐릭터 직접 AniList 대체 조회는 제거했다. 카탈로그 캐릭터의 숫자형 외부 ID를 기존 즐겨찾기·감상 참조와 연결했다. 깨끗한 Git checkout에서 단위 440개, 관련 Chromium 9개, Web build 20페이지가 통과했다. 카탈로그 검사는 256개 통과·2개 환경 건너뜀. 운영 후보와 원천·DB 사본은 Git 밖 `D:/hong/Web/Anime/.moemoa-character-audit-2026-10-08/`에 보관한다. 승인된 DB release가 활성화되었고 46개 미바인딩과 AniList에도 캐릭터가 없는 68개는 남는다. 이 기록 작성 시점에 Git push·Web 배포는 아직 진행 중이다.
