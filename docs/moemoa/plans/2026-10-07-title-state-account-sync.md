# 작품 기록 계정 동기화 ExecPlan

## 1. 목적과 사용자 결과

같은 계정으로 로그인한 PC에 저장 작품 51개가 보이지만 iPhone Safari에는 0개가 보이는 현상을 해소한다. 작품 저장 상태, 평점, 감상 기록, 컬렉션 선반 구성을 기기 사이에서 안전하게 이어받고, 동기화 완료 표시가 실제 포함 범위를 분명히 말하도록 한다.

## 2. 관련 확정 결정

`SYNC-01`은 Memory/Board 정규화 동기화를 확정하고 작품 상태·WatchLog의 원격 동기화는 `TITLE-STATE-SYNC-01` 결정 전 자동 추가하지 않도록 했다. 2026-10-07 사용자는 백업 파일 수동 이전보다 같은 계정에서 재발하지 않는 동기화 해결을 명시적으로 요청했다. 이 작업의 결정 범위는 비공개 작품 상태와 감상 기록이며, 이미지·Public·Android 네이티브는 포함하지 않는다.

## 3. 현재 상태와 저장소 증거

- `src/components/DataCenter.jsx`는 `useMemoryAccountSync`만 연결한다. `src/hooks/useSyncStatus.js`는 UI에서 사용되지 않는다.
- `src/repositories/titleLibraryRepo.js`는 AniList 기반 목록과 자체 카탈로그 목록을 서로 다른 로컬 저장소에서 합친다.
- `src/features/bookshelf/bookshelfSettings.js`의 컬렉션 선반은 owner별 기기 로컬 설정이다. 작품만 동기화하면 컬렉션은 여전히 비어 보일 수 있다.
- `src/repositories/syncRepo.js`의 이전 동기화는 AniList ID 기반 Library/WatchLog만 취급하고 서버 행을 목록 단위로 삭제할 수 있어 그대로 복원하지 않는다.
- 2026-10-07 운영 PC UI에서 저장 작품 51개, 감상 기록 22개를 확인했고 로컬 백업 파일의 건수와 일치했다. iPhone Safari 같은 계정은 동기화 완료 뒤 작품 0개라고 사용자가 보고했다.

## 4. 범위

### 포함

- AniList/자체 카탈로그 작품의 비공개 저장 상태·평점·메모·재시청 상태, WatchLog, 컬렉션 선반 구성의 계정 동기화.
- 첫 동기화 시 기존 로컬 자료를 보존하며 서버 자료와 합친다. 삭제는 tombstone, 충돌은 명시적 해결.
- 계정 변경 fence, 네트워크 실패 복구, 상태·오류 표시, 실제 PC→iPhone 검증 절차.

### 제외

- 개인 이미지 바이트, Memory/Board 저장 모델 변경, Public, Android 네이티브, 기존 사용자 자료의 일괄 삭제.

## 5. 아키텍처·데이터 흐름

작품 key는 `anime:<UUID>` 우선, 없으면 `anilist:<positive integer>`로 고정한다. 서버는 owner별 정규화 행, 버전, server timestamp, tombstone을 둔다. 로그인 후 먼저 양쪽 목록을 읽고 로컬 마지막 확인 버전과 비교해 변경분만 적용한다. 다른 기기 변경을 먼저 받아들이되 같은 행의 양쪽 변경은 자동으로 덮어쓰지 않는다. 클라이언트의 낡은 빈 목록으로 서버의 51개를 삭제하지 못하게 한다.

## 6. 변경 파일 지도

- `supabase/migrations/`: owner RLS와 버전 조건이 있는 작품/감상 기록 행·RPC.
- `src/repositories/`, `src/hooks/`: 로컬/서버 조정과 UI 상태.
- `src/components/DataCenter.jsx`, 관련 메뉴/문구: 작품 기록 동기화 범위와 충돌 표시.
- `tests/`: 첫 동기화, 병합, 충돌, 삭제, 다른 계정, 오류 재시도.

## 7. 데이터·스키마 마이그레이션

기존 로컬·서버 기록은 지우지 않는다. 새 테이블은 additive이며 기존 AniList 원격 행은 별도 읽기/전환 검증 후 처리한다. 운영 적용 전 현재 자료 백업과 대상 계정의 건수 대조가 필요하다.

## 8. 마일스톤

1. 서버/로컬 계약과 충돌 테스트를 먼저 통과시킨다.
2. PC 51개·22개를 잃지 않고 첫 원격 등록할 수 있게 한다.
3. 빈 iPhone이 같은 계정의 작품/감상 기록을 받아들인다.
4. 다른 기기에서 추가·수정·삭제한 뒤 다시 왕복해 수렴한다.
5. 검토된 migration/코드만 Git 경로로 배포하고 실제 양기기 수치를 확인한다.

## 9. 테스트와 검증

단위 계약, 격리 DB RLS/충돌, 브라우저 2세션, 기존 백업 복원, 빌드. 운영에서는 소유자 계정의 사전/사후 건수만 확인하고 개인 제목·메모를 로그로 남기지 않는다.

## 10. 보안·개인정보·권리 영향

서버에서 `auth.uid()` owner를 검증하며 기록은 비공개로 둔다. 제목·메모·감상 내용은 일반 로그/분석에서 제외한다. 이미지 업로드와 공개 범위는 변경하지 않는다.

## 11. 관찰 가능성·분석 이벤트

동기화 성공/실패/충돌 건수만 로컬 상태에 표시한다. 계정 식별자와 개인 내용은 출력하지 않는다.

## 12. 롤백·복구

PC 백업 파일을 보존한다. UI 기능 플래그를 끄면 기존 로컬 읽기를 유지한다. DB additive migration은 롤백 시 자료를 삭제하지 않는다.

## 13. 위험과 완화

기존 로컬 목록이 계정별로 분리돼 있지 않으므로 자동 업로드 전에 계정 귀속 여부를 확인한다. 동일 작품이 두 ID를 가지는 경우 무리하게 합치지 않는다. 원격 오류 시 로컬 자료는 유지한다.

## 14. 필요한 사용자 결정

작품 기록을 계정 동기화 범위에 넣는 방향은 2026-10-07 사용자의 재발 방지 요청으로 확정한다. 운영 DB 적용·Git 운영 배포는 저장소 `AGENTS.md`의 명시적 운영 배포 승인 gate에 따라 검증 결과를 제시한 뒤 결정한다.

## 16. 발견 사항과 계획 변경

기존 복합 snapshot 동기화 재활성화는 자체 카탈로그 누락 및 목록 삭제 위험 때문에 채택하지 않는다.
