# MOEMOA 제품·구현 분석

검토 대상: `MOEMOA-Pro-Review-2026-09-09.zip` / 작성: 2026-09-11 / 상태: **분석 및 개선 제안**

## 1. 총평

**이전의 ‘Library와 Memory를 어떻게 연결할까’라는 구조적 질문에는 이미 상당 부분 답이 구현되어 있다.** 이제 필요한 것은 메뉴 재설계가 아니라, 처음 기록한 사람이 두 번째 기억을 같은 작품에 남기고, 그것을 찾아보고, 안전하게 보관할 수 있도록 남은 연결을 마무리하는 일이다.

표지 전용 갤러리를 폐기하거나 강제로 Memory 카드형 목록으로 바꾸는 방향은 권장하지 않는다. 현재 복원한 표지 그리드·태그·열 조절은 유지할 가치가 있다. ‘기억 함께 보기’와 Board의 표현·행동을 개선해 두 모드의 차이를 완성해야 한다.

**현재 판정:** 핵심 정상 사용 경로가 돌아가는 프로토타입이다. 제한된 사용성 테스트를 진행할 근거는 있으나, 기록 보관을 약속하는 일반 공개 베타의 품질 승인을 내릴 자료는 부족하다. 새로운 기능 수보다 데이터 정합성, 재기록, 재열람, 복구가 우선이다.

## 4. 우선 해결할 문제

### 4.1 공식 표지 카드의 완료 조건이 ‘수정’ 경로에서 깨진다 — P0 / 별도 재현

생성 시에는 감상이 없는 공식 표지 카드를 막는다. 그러나 `createUpdateMemoryCardCommand`는 감상을 빈 문자열로 바꾸는 것을 허용하고, 실제 IndexedDB의 `updateCardMetadata`도 해당 값을 그대로 저장한다.

별도 재현 R02에서는 정상 생성된 표지 카드의 유일한 개인 신호인 note를 지운 뒤, command가 `COMPLETE_PRIVATE, note=null`을 반환했다. 같은 결과를 `assertCompletePrivateCard`에 넣으면 `CATALOG_COVER_PERSONAL_SIGNAL_REQUIRED`로 거절된다. 제공된 SQL에도 같은 개인 신호 조건이 있다.

**의미:** 화면에서는 저장 성공한 기록이 로컬 도메인 규칙과 맞지 않는다. 서버 동기화 거절은 SQL에 근거한 예상이며 실제 계정에서 실행하지 않았다.

**수정:** 생성/수정/이미지 교체/복원에 동일한 complete-card validation을 적용한다. 빈 감상 업데이트를 미리 막고 현재 카드 값은 보존한다. 다른 유효한 개인 신호가 있으면 그 조건을 정확히 인정한다. 자동으로 의미 없는 문구를 넣거나 몰래 카드 상태를 바꾸지 않는다.

근거: E07~E11, `evidence/review-reproductions.json` R02.

### 4.2 개인 작품에 ‘두 번째 기억’을 남기는 경로가 끊겨 있다 — P0 / 소스+별도 재현

Title Hub의 작성 CTA는 `album.titleRef.kind === "ANIME"`일 때만 보인다. PrivateTitle은 허용된 기록 모델인데, 해당 작품 화면에서 같은 작품으로 새 기억을 시작할 수 없다.

다시 Composer에 같은 문자열을 입력하면 생성 명령이 새 `privateTitleId`를 만든다. R01에서 같은 제목 두 번 입력은 두 개의 작품 ID와 각각 기억 1개의 앨범으로 나뉘었다.

이는 ‘동명 작품을 자동으로 합쳐야 한다’는 뜻이 아니다. **기존 개인 작품을 명시적으로 다시 선택할 방법이 필요하다는 뜻**이다.

**수정:** PrivateTitle 허브에도 `기억 남기기`를 제공하고 기존 ID를 Composer로 전달한다. 생성 명령은 신규 개인 작품 생성과 기존 개인 작품 선택을 구분하고 owner 일치를 검증한다. 기존 동명 데이터를 자동 병합하지 않는다. 개인 작품을 공용 작품에 연결하는 기능은 별도 선택적 전환으로 설계한다.

근거: E05, E06, E07, E21, R01.

### 4.3 백업은 최신 제품 데이터 전체를 포함하지 않는다 — P0 / 소스 확인

수동 백업 화면이 이미 ‘기록장 / 티어 / 감상 기록’ 범위를 표시한 점은 개선이다. 따라서 UI가 모든 Memory를 백업한다고 명시적으로 주장한다고 단정하면 안 된다.

하지만 `exportSyncSnapshot`은 기존 Library, Tier, WatchLog, character pins, 일부 preference를 읽는다. Memory/Board/개인 이미지뿐 아니라, AniList ID가 없는 공용 작품의 별도 저장소 `moemoa:catalog-saved-titles:v1`도 읽지 않는다. DataCenter의 저장 수 집계도 기존 Library 위주다.

**의미:** ‘내 작품’에 저장한 항목조차 출처에 따라 백업에서 빠진다. Memory-only 사용자에게 저장한 작품/기억이 충분히 있는데 기존 지표는 0일 수 있다. 파일을 내보냈다는 성공 표시와 실제 보호 범위가 다르다.

**수정:** 먼저 데이터별 포함/미포함, 기기 전용/서버 기록/이미지 파일을 정확히 표시한다. 이어서 최신 메타데이터 export/import를 별도 버전으로 지원하고 깨끗한 저장소에서 round-trip을 검증한다. 사용자 이미지 파일 미포함은 계속 명확히 알린다. 클라우드 이미지 백업까지 묶어 이번 작업을 확대할 필요는 없다.

기존 import는 여러 저장소를 순차 변경하고 일부 legacy write의 IndexedDB 완료를 기다리지 않는다. fault injection으로 부분 성공을 검증하고, snapshot 검증→변경 미리보기→복구 지점→커밋 순서를 추가한다. 실제 데이터 손실은 이번에 재현하지 않았다.

근거: E12~E15.

### 4.4 자체 카탈로그 작품의 시청 관리가 AniList 연결 유무에 따라 달라진다 — P0 / 소스 확인

작품은 자체 내부 ID로 저장할 수 있지만, TitleFacts의 편집 링크와 WatchLog 조회는 `anilistId`가 있어야 열린다. 시청 상태를 제공하는 제품에서 작품의 외부 출처가 기능 가능 여부를 결정하면 사용자는 이유를 알 수 없다.

**수정:** TitleRef 기반의 작은 로컬 시청 상태/평점 편집을 Title Hub 안에 둔다. legacy adapter는 호환용으로 남긴다. 신규 원격 Title 상태 sync까지 자동 확장하지 않는다. WatchLog를 이번 베타에서 모든 작품에 제공할지, 일부 고급 기록을 보조 기능으로 남길지는 명시적으로 결정한다.

근거: E05, E14, E24.

### 4.5 평점 미입력이 0점으로 바뀐다 — P0 수정에 함께 포함 / 별도 재현

`Number.isFinite(Number(item?.score))`는 `null`도 0으로 변환한다. R03에서 원본 `score:null`이 projection의 `rating:0`이 되었다. 원본 저장 값 자체가 바뀌었다는 뜻은 아니다.

**수정:** null/undefined/빈 문자열을 먼저 미평가로 보존한다. 실제 0점은 별도로 유지한다. 정렬·요약·영문/한글 표시에서 동일 정책을 적용한다.

근거: E06, R03.

### 4.6 Board가 이미지 모음이 아니라 텍스트 관리 목록으로 끝난다 — P1 / 화면+소스

보드의 연결/정렬은 있지만, 읽기 화면은 작품 제목과 감상 행이며 이미지를 렌더링하지 않는다. 이미지 중심 기록을 주제로 모은 뒤 가장 기대하는 ‘한눈에 다시 보기’가 없다.

**수정:** 도메인은 그대로 두고 읽기 화면을 공통 Memory Gallery로 바꾼다. 편집 버튼을 누를 때만 정렬·제거·삭제를 노출한다. Archive와 Memory 상세에 `보드에 담기`를 추가해, 보드에 먼저 들어가 텍스트 후보 중 하나씩 찾는 왕복을 줄인다. 드래그만 강제하지 말고 기존 키보드용 위/아래 이동은 유지한다.

근거: E16 및 화면 30/31/45.

### 4.7 Memory View는 존재하지만 개인 이미지를 훑고 여는 경험이 약하다 — P1 / 화면+소스

미리보기 1개에도 항상 3열 프레임을 적용해 카드의 일부 폭만 사용한다. 시스템 디자인의 상세 텍스트가 아주 작은 썸네일에서 세로로 찢어져 보인다. 미리보기는 클릭 링크가 아니어서 이미지를 눌러 그 기억을 열 수 없다.

**수정:** 1/2/3개에 맞는 preview 배치와 전용 thumbnail 렌더러를 둔다. 썸네일은 실제 Memory 상세 링크여야 한다. 작은 시스템 디자인에서는 장식·바탕을 유지하되 footer/preview label을 줄이고 제목은 바깥쪽 텍스트에서 읽게 한다. 표지 전용 모드의 촘촘한 갤러리는 바꾸지 않는다. 표지가 없는 개인 작품 타일에만 실제 개인 작품명을 넣어 식별 가능하게 한다.

근거: E18, E22 및 화면 42/46/50.

### 4.8 Home과 Archive 역할이 겹치고, 실패가 ‘없음’처럼 보이는 지점이 있다 — P1(실패 분리는 P0)

반복 방문 Home의 실제 제목은 ‘기억 아카이브’이고 한 장의 큰 최근 Memory가 대부분을 차지한다. Archive는 같은 이름의 전체 Gallery다. Home은 최근 기억·최근 작품으로 돌아가는 출발점이어야 한다.

또한 Title Hub는 load exception을 not-found로 처리하고 Memory Detail도 error/not-found를 같은 문구로 보여준다. 저장된 기록을 못 읽는 상황과 기록이 없는 상황은 분리해야 한다. 자동 초기화나 삭제로 해결하지 않는다.

화면 지도는 Archive의 검색/필터를 언급하지만 현재 `ArchiveView.jsx`와 캡처에는 그 입력이 없다. 이 부분은 **문서보다 실제 소스·화면을 기준으로 미구현**으로 기록한다.

근거: E05, E17, E20 및 화면 11/12/40/41.

## 5. 추천하는 메인 경험 하나

### 대상 사용자와 첫 세 번의 의미 있는 행동

대상은 시청 수량만 관리하려는 사람보다 **애니를 본 뒤 장면이나 감상 한 줄을 남기고, 나중에 작품/이미지/주제로 다시 꺼내 보려는 사람**으로 정의하는 것이 현재 구현과 맞는다. 실제 시장 수요가 검증되었다는 주장은 하지 않는다.

웹 첫 방문은 다음 세 가지 행동을 중심으로 정리한다.

1. 작품을 찾고 고른다.
2. 기억을 남긴다: 승인 표지를 명시적으로 선택하거나 시스템 디자인을 고르고 한 줄 감상을 적는다.
3. 저장된 결과를 보고 같은 작품에 쌓이는 위치를 이해한다.

이는 클릭 세 번에 반드시 끝내라는 요구가 아니다. 사용자가 처음 배우는 개념을 작품/내 기억/다시 보기에 한정한다는 뜻이다.

### 왜 Web에서는 작품부터인가

| 방식 | 현재 Web에서의 장점 | 비용 | 판정 |
|---|---|---|---|
| 빈 Visual 선택부터 | Android와 화면 순서가 동일 | 사진 입력이 안 되고 표지는 작품 선택 뒤에야 등장 | 일반 Web의 기본 출발점으로는 약함 |
| 작품 선택 후 기억 작성 | 이미 가능한 공식 표지 경로가 자연스럽고 입력 이유가 분명함 | 개인 작품 fallback이 필요 | **웹 기본 경로로 권장** |

`기억 남기기` CTA는 유지하되, 미리 선택한 작품이 없으면 Composer의 작품 선택 단계로 시작한다. 작품 상세에서 들어오면 선택이 채워져 있으므로 바로 Visual과 감상으로 진행한다. 표지를 자동 적용해 이미 사용자가 선택한 것으로 처리하지 않는다.

Android Share Target은 이미지가 이미 있으므로 **이미지 → 작품 → 기억 → 저장**을 그대로 유지한다. 서로 다른 클라이언트에 동일한 화면 순서를 강제할 필요가 없다. 핵심 결과와 domain contract가 같으면 된다.

### 작품만 저장하는 분기

작품 검색/상세의 `작품 저장`은 계속 허용한다. 상태와 평점은 선택적이다. 저장 완료 뒤 Memory를 강제로 생성하거나 Composer로 강제 이동하지 않는다. `나중에 기억 남기기`로 연결하고 사용자가 목록 관리만 하고 떠날 수도 있게 한다.

### 재방문과 보드

`홈 → 최근 기록 이어보기` / `내 작품 → 표지로 작품 찾기 → 해당 기억` / `기억 → 장면으로 찾기`를 모두 유지한다. 카드가 쌓인 뒤 선택한 카드에서 `보드에 담기`를 제공한다. 보드 생성을 카드 저장의 선행 조건으로 두지 않는다. 계정은 실제 동기화 범위를 설명한 뒤 선택적으로 연결한다.

### 화면 역할·내비게이션

- 홈 / Home: 최근 기억·최근 작품과 다음 기록 행동. 전체 아카이브를 반복 복제하지 않는다.
- 작품 / Titles: 표지 또는 작품별 앨범으로 탐색. 현재 두 보기·태그·열 조절 유지.
- 기억 / Memories: 완성 카드의 전체 갤러리와 카드 찾기.
- 보드 / Boards: 여러 작품의 기억을 개인 주제로 다시 보는 공간.

데스크톱 최상위 4개는 유지해도 된다. 구조 문제가 해결되기 전에 다시 메뉴를 합치거나 순서를 바꾸는 것이 우선은 아니다. 모바일도 현재 로고/기억 작성/검색/메뉴를 유지하고 핵심 왕복 링크부터 개선한다. 프로필·티어·옛 시청 편집·스토리지 진단은 부가/설정 영역이다. 새 하단 내비게이션은 필수 변경으로 묶지 않는다.

## 6. 기능/출시 판단

| 범위 | 현재 판단 | 다음 gate |
|---|---|---|
| 감독 가능한 사용성 테스트 | 가능한 핵심 흐름의 근거 있음 | 테스트 기록은 복구 불가할 수 있음을 안내; 기존 데이터 사용 안 함 |
| 소규모 Web 개인 기록 베타 | 조건부 | R02/R01, null 평점, 자체 작품 편집, 저장/복구 범위, 실패 UX, 재열람/보드 핵심 보완 |
| 계정·다기기 기능 포함 베타 | 별도 검증 필요 | 실제 OAuth, 승격, 다른 계정, 충돌·삭제 전파, 로그아웃 후 로컬 데이터 |
| Android 베타 | 별도 검증 필요 | 최신 Web 변경 반영 빌드, 실제 이미지/공유/취소/재시작/복구 |
| Public 서비스 | 이번 완료에 포함 불가 | 게시/권한/비공개 누출 방지/신고/차단/운영 gate |

베타에 처음부터 이미지 클라우드·공개 프로필·추천·티어 고도화·카탈로그 완전 정제를 모두 요구하지 않는다. 반면 아카이브의 저장/재열람/내보내기 보장은 핵심 제품 책임이므로 미루기 어렵다.

## 7. 데이터·운영 이슈는 별도 트랙으로

ZIP은 카탈로그 4,292개, 추가 131개, 보류 6개, 일부 표기와 재생성 목록 통합 과제를 기록한다. 이는 제공 자료의 상태 보고이며 이번 분석에서 운영 DB를 재집계하거나 이름을 전수 검증한 결과는 아니다. 카탈로그 정제만 하느라 이번 UI 개선을 미루지 않는다.

GitHub HEAD와 운영 직접 배포의 불일치도 제공 자료의 사실이다. 웹 빌드의 commit SHA/배포 ID와 카탈로그 release를 별도 관리하고, 미푸시 소스를 보존한 뒤 Git 배포 경로를 정리한다. 배포나 카탈로그 원본을 임의로 덮어쓰지 않는다. 소스 스냅샷은 있지만 원본 수집 workspace 전체는 없으므로 완전 데이터 재현까지 보장하지 않는다.

## 8. 최종 우선순위

**첫째, 기록의 정합성과 안전:** 표지 카드 수정 조건, PrivateTitle 재사용, 자체 작품 상태, null 평점, 데이터 범위·복구, 실패 분리.

**둘째, 다시 볼 가치:** Memory View 미리보기, 이미지 Board, 읽기 우선 Memory Detail, Home 역할, Archive 최소 검색.

**셋째, 범위별 검증:** 실제 Web 사용자 테스트와 계정/Android/Public을 별도로 닫는다.

현재의 제품 구조는 유지할 만하다. 다음 마일스톤은 기능을 더 늘리는 것이 아니라 **‘기억 한 장을 만든 뒤 두 번째를 쌓고, 다시 찾아보고, 안전하게 보관할 수 있다’**를 입증하는 마일스톤이어야 한다.
