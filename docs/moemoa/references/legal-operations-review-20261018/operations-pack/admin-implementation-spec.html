1.미완료 법정 기한이 지났거나 가까운 사건.

3.조치는 했지만 사본 확인·당사자 통지가 남은 사건.

‘법적 요건 검토 중’은 ‘법정 기한 없음’으로 보여주지 않는다. 아직 판정하지 않았다는 사실을 상단에 띄운다. 한 번 확인한 경보는 확인자와 다음 점검시각을 남겨 같은 줄을 계속 새 사건으로 만들지 않는다. 원인과 심각도가 바뀌면 다시 알린다.

사건 상태와 해결 기준

원본 신고의 RECEIVED / APPEALED / CLOSED를 바꾸지 않고 운영 메타데이터를 별도로 둔다.

운영 상태의미빠져나오는 조건
NEW / 신규접수됐지만 운영자가 아직 확인하지 않음확인자·시각, 초기 분류·다음 기한 기록
ACTIVE / 처리 중사실·범위 확인 또는 조치 진행조치가 완료되거나, 구체적인 보완 요청·후속 단계가 생김
WAITING_REQUESTER / 보완 대기꼭 필요한 추가 정보 요청을 기록정보 수령 또는 이유를 기록한 다음 판정. 자동 법정 기한 중단 없음
FOLLOW_UP / 후속 확인공개 조치, 사본 확인, 통지, 운영 복구 중 일부가 남음사건별 필수 완료 증거가 모두 존재

DUPLICATE / 중복 연결기존 사건과 같은 범위로 확인해 연결원접수시각·신청인 상태 조회를 보존하고 상위 사건을 따름

‘공개 가림’ 버튼이 성공하면 원본 신고는 CLOSED일 수 있다. 이때 알려진 다른 공개 사본이 2개 남아 있으면 운영 사건은 FOLLOW_UP다. 관리자 메일 실패만으로 원본 신고 판정이나 공개 조치를 되돌리지 않는다.

종결 전 필요한 증거는 사건 종류에 맞게 정한다. 단일 스팸 사건에는 판정·대상 노출 결과·앱 통지가 필요하다. 유효한 동일 이미지 삭제 요청에는 알려진 사본 탐색 범위·각 조치·직접 이미지 경로 확인·신청자 결과 안내가 추가된다. 단순 관측 경보에는 새 관측과 다음 확인시각이면 충분할 수 있다.

5. 심각도·법정 기한·내부 목표

심각도와 법률 적용 여부는 서로 다른 필드다. 자동화는 위험 신호를 정렬할 수 있지만 신고 분류만으로 범죄나 침해 사실을 확정하지 않는다.

운영자가 내부 목표를 변경해도 법정 마감은 변하지 않는다. 법정 기준은 아래처럼 적용 확인된 규칙으로 연결한다. 법률 문서는 별도 정책 초안과 함께 검토·공개해야 한다.

반드시 저장할 시각

•received_at: 실제 서비스/메일함에 처음 도착한 시각. 외부 메일 수기 접수라면 원문 도착 시각과 접수한 운영자를 기록한다.

•trigger_received_at: 해당 법률상 유효 요건이 처음 모두 갖춰진 요청을 받은 시각. 운영자가 나중에 유효성을 확인한 시각과 다르다.

•validated_at: 운영자의 유효성/적용 판정 시각.

•statutory_due_at: 적용 규칙과 trigger 시각으로 계산한 마감. 원접수·기존 유효 시각은 보존한다.

•internal_due_at: 운영자의 더 이른 목표. 필요하면 변경하되 이유와 전후값을 감사에 남긴다.

•단계별 completed_at: 노출 조치, 동일 사본 확인, 통지 등의 실제 완료시각.

한 사건에 여러 단계별 법정 기한이 있을 수 있으므로 법정 마감 하나로 모든 것을 덮지 않는다. 한국 저작권 중단·통지·재개 절차와 개인정보 권리 요청은 서로 다른 rule ID다. 한국의 기간과 미국 DMCA 기간을 공통 상수로 만들지 않는다.

TIDA 요청용 접수와 처리

미국 FTC가 설명하는 covered platform에 해당하는 경우, 유효한 비동의 사적 이미지 삭제 요청을 받은 뒤 가능한 한 빨리, 늦어도 48시간 내 대상과 알려진 동일 사본을 처리해야 한다. MOEMOA는 개인 기록 중심에 선택적 공개 기능이 있으므로, 실제 주목적이 UGC forum인지·다른 적용 요건이 있는지·미국 관할이 미치는지는 별도 사실 판단이 필요하다. 미국 가입과 공개 이미지 기능만으로 적용을 확정하지 않는다.

현재 운영 설계에는 48시간과 알려진 동일 사본을 다룰 준비를 포함하되, 실서비스의 초기 platform_applicability는 REVIEW_REQUIRED로 두고 판단 근거·규칙 버전을 남긴다. 플랫폼 적용성·관할·개별 요청의 유효성은 구분한다. 적용 미확정 상태에서 자체적으로 정한 48시간 목표는 ‘내부 목표’로 표시한다. 법정 기한으로 확정한 것처럼 표시하지 않는다. 공식 근거는 문서 끝에 있다.

로그인 없는 요청 화면/메일 양식에는 다음을 받는다.

1.요청하는 본인 또는 권한 있는 대리인의 실물/전자 서명에 해당하는 표시.

2.합리적으로 찾을 수 있는 공개 URL 등 문제 콘텐츠 식별·위치.

3.동의 없이 공개되었다는 선의의 믿음의 짧은 진술과 관련 정보.

4.연락 가능한 충분한 연락처.

신분증, 문제 이미지 재업로드, 경찰 신고번호, 저작권 소유 증명은 이 경로의 일괄 필수 항목으로 만들지 않는다. 실존 인물을 식별할 수 있는 사진·디지털 위조 등 해당 요건을 확인하고, 가상 캐릭터 그림이라는 이유만으로 TIDA 48시간 사건으로 자동 분류하지 않는다. 일반 서비스 정책의 조치와 법적 삭제 요청 절차는 함께 기록할 수 있다.

서면 요청의 요건이 이미 갖춰졌다면 운영자의 확인이 늦었거나 보완 질문을 보냈다는 이유로 48시간 시계를 뒤로 밀지 않는다. 같은 이미지의 사본별로 다시 신고하라고 요구하지 않는다. 저작권 이의 절차가 끝났다는 이유만으로 NCII 관련 차단을 자동 해제하지 않는다.

6. 단일 대상 가림과 알려진 동일 이미지 처리

현재 review_memory_report(HIDE)는 해당 보드 또는 해당 미니홈의 hidden 상태를 바꾼다. 미니홈을 가려도 별도 보드가 살아 있을 수 있고, 같은 이미지를 쓰는 다른 보드·다른 공개 사본까지 한 번에 처리한다는 계약은 없다.

memory_public_assets에는 source_asset_id, source_version, source_hash, full_hash, thumb_hash가 있다. 이 정보와 공개 snapshot의 assetId 참조를 사용하면 이미 알려진 서비스 내부 공개 사본의 목록을 만들 수 있다. 이는 모든 재인코딩·크롭·색변경 이미지를 시각적으로 찾아내는 기능이 아니다. 원래 업로드가 다른 경우 source hash도 달라질 수 있으므로 신고자가 알려 준 별도 URL, 파생 관계, 이미 확인한 사본을 함께 묶는다.

법률상 사본 범위를 공개 사본으로만 한정하지 않는다. TIDA의 known identical copies 문언에는 공개 여부로 자동 제외한다는 한정이 없다. 공개 asset의 source 연결로 이미 알려진 비공개 원본·사본이 있다면, bytes를 열거나 삭제하지 않고도 그 연결과 미해결 여부를 제한된 메타데이터로 기록할 수 있다. 현 owner 경계를 유지하면서 해당 비공개 항목이 어떤 법적 처리 대상인지 별도로 판단해야 한다. 이번 공개 조치만 성공했다고 법률상 모든 사본의 처리가 완료됐다고 선언하지 않는다. 비공개 원본에 대한 추가 접근·조치가 필요한 경우 정확한 법적 근거·최소 범위·별도 승인 계획으로 다룬다.

제안하는 사건별 조치 흐름

1.노출 억제: 위험이 크고 근거가 있는 경우 신고 대상의 임시 가림을 개별 승인한다. 목록에는 ‘대상 가림 완료, 사본 조사 중’으로 보인다.

2.범위 찾기: 해당 공개 asset에서 source 연결·정확 hash 일치와 알려진 URL을 따라 공개 보드·미니홈 전시·현재/준비 snapshot·full/thumb 경로를 모은다. 비공개 원본 bytes를 가져와 전수 스캔하지 않는다.

3.후보 고정: 사건 revision, 각 공개 대상/source revision, 발견된 사본 수, 처리할 조치, 관련 정책과 법정 기한으로 targetSetHash를 만든다. 공개 원본의 경로·사용자 개인 기록은 프런트엔드에 반환하지 않는다.

4.한 번의 승인: 운영자는 ‘보드 2개·공개 사본 3개에 대한 공개 제공 중단’과 사유를 확인한 뒤 제출한다. 대상 집합이나 revision이 바뀌면 다시 읽고 다시 결정한다. 일반 확인 한 번으로 미래의 모든 사본을 무기한 삭제하는 권한을 만들지 않는다.

5.공개 경계에 적용: 현재 source/representation 권리 경계와 별도의 조치 이력을 사용해 알려진 사본의 공개 제공을 막는다. 기존 자기선언 함수는 revoked source의 재승인을 허용하지 않는 경계가 있으므로 재사용 가능성을 검토한다. 여러 사건의 제재가 겹치면 한 사건 해제가 다른 사건의 차단을 풀지 않도록 해야 한다. 광범위 revoked_at = null 복구 버튼은 만들지 않는다.

6.경합 확인: prepare/upload/publish/read와 소스 철회 경로의 현재 lock 순서를 지킨다. 발견 이후 같은 소스에서 추가된 공개 사본은 완료 전 재조회해 미처리로 표시한다. 조치 전후 직접 이미지 경로의 차단을 확인한다.

7.사본 정리 구분: 공개 차단, 공개 참조 제거, 저장 bytes의 물리 정리는 별도 결과다. 현재 cleanup은 참조된 asset을 제외한다. HIDE만으로 snapshot 참조가 없어지는 것은 아니므로, ‘가렸으니 다음 cleanup에서 삭제된다’고 약속하면 안 된다. 물리 제거까지 필요하면 정확한 공개 참조·공개 사본에 한정한 명시적 후속 계획을 승인하고 실행한다. 이 공개 조치는 비공개 사용자 원본/카드를 자동으로 변경하지 않는다.

8.결과 통지·종결: 알려진 사본 목록, 처리 또는 미처리 이유, 각 확인 결과, 신청자 안내 기록을 남긴다. 공개 사본 조치 완료와 법률상 사건 완료를 나눈다. 알려진 비공개 source의 법적 검토·필요 조치가 미해결이면 이를 숨기고 사건을 해결로 바꾸지 않는다. 정리가 남아 있으면 그 사실을 구분해서 표현하고 법적 요구의 충족을 과장하지 않는다.

긴급 검토를 위해 현재 전역 전송 한도를 우회하지 않는다. quota 429 또는 네트워크 오류만 보고 사본이 삭제됐다고 판정하지 않는다. 의미 있는 검증은 정책상 차단 결과와 이미지 bytes 미반환을 확인하는 것이다.

이 영역은 UI 버튼 두 개만 추가하는 작업으로 산정하지 않는다. 공개 경계와 동시성의 실제 영향이 있으므로 별도 구현·검사가 필요하다.

7. 화면 설계: 필요한 필드와 행동

A. 오늘 할 일 — /admin/ 기본 화면

상단: 환경 배지(검토본/운영), 운영자 권한 배지, 기준 시각 KST, 마지막 데이터 조회 시각, 데이터 상태 확인됨/오래됨/확인 실패, 수신자 godburgundy@gmail.com, 발신 연결 상태.

요약 카드 4개: 미확인 긴급, 오늘 마감, 조치 후 미완료, 실패한 운영·보고. 숫자는 클릭 가능한 필터다. 값이 없으면 0이 아니라 ‘미확인’이다.

목록 열: 사건 번호, 안전한 제목, 유형, 심각도, 운영 상태, 가장 이른 기한(법정/내부 구분), 마지막 사건 발생 시각, 다음 할 일, 담당 확인 여부. 모바일에서는 사건·기한·다음 할 일을 먼저 보이게 한다.

행동: 사건 열기, 확인 기록, 정해진 다음 점검시각 설정, 관련 검토 화면으로 이동. 가림/삭제/제재를 목록에서 무확인 일괄 실행하지 않는다.

B. 사건 상세 — /admin/?case=<opaque-id>와 기존 /moderation/

위쪽: 원접수, 유효 요청 접수, 분류/유효성 확인, 내부 목표, 법정 단계별 기한. 임박·초과는 색 이외 텍스트로 표시한다. 아래에는 네 개 영역을 둔다.

•요청/증거: 접수 채널, 공개 대상 링크, 필요한 요청 내용, 요청 요건 체크, 추가 자료/회신 기록. 원문은 허용된 역할로 상세를 열 때만 요청한다.

•조치: 단일 대상 유지/가림/가림 해제, 콘텐츠 분류, 필요한 경우 사건별 공개 쓰기 제한. 실행 전 현재 target/revision과 작성자 통지 사유를 함께 보여준다.

•동일 사본: 알려진 공개 사본 수, 발견 근거, 보드/공개 사본 단위 목록, 조치 상태, 직접 응답 확인. 알려진 비공개 source 연결은 내용·저장 경로 없이 별도 법적 검토 상태로 표시한다. ‘전체 확인’ 범위가 어떤 목록인지 문장으로 설명한다.

•통지/감사/해결: 앱 알림 생성, 외부 답변 초안/실제 전송 기록, 운영 메일 상태, 관련 조치와 원본 감사 링크, 해결 조건.

필수 행동은 ‘사건 처리 저장’과 ‘공개 조치 실행’을 나눈다. 메모 저장 때문에 공개 상태가 바뀌면 안 된다. 조치의 사유·대상·revision을 바꾸면 체크박스가 해제된다. 응답이 끊긴 경우 버튼을 다시 누르게 하기 전에 동작 ID로 결과를 조회한다.

C. 서비스 상태

현재 가입 상태/최소 연령/약관 버전은 그대로 보여준다. image quota는 범위(계정/서비스 전체), 수치, 단위, 사용량 창, 관측 시각을 나눈다.

보호값: 비공개 사본 전역 100,000,000 B, 비공개 월 전역 500,000,000 B, 공개 사본 전역 20 MiB, 공개 2,000 GET와 64,000,000 B/UTC일, 전체 저장 980 MB 경보. 설정값은 실제 현재 사용량이나 수용 가능한 회원 수가 아니다. 공개 전송에는 미리보기/관리자/재시도 예산도 포함될 수 있다.

정리/백업/health 행에는 예정, 최근 시도, 최근 성공, 단계 결과, 다음 예상, 늦음 여부, 근거 실행 링크를 함께 둔다. cleanup 성공과 경보 발생은 동시에 가능하다. 실제 관측 스크립트는 경보만으로도 실패 exit code를 낼 수 있으므로 GitHub conclusion만으로 삭제 실패라고 설명하지 않는다.

허용 행동: 갱신, 실행 기록 열기, 관측만 다시 실행하는 승인 후보 확인. 백업 복원·원본 삭제·baseline 교체·quota 증액은 일반 버튼으로 제공하지 않는다.

D. 보고와 전송 상태

일일/긴급/주간 탭, 해당 기간, 보고 생성 시각, 관측 데이터 시각, 수신자, 템플릿 버전, 상태, 시도 횟수, 다음 재시도, 마지막 안전한 오류 코드, provider 접수 ID, 운영자 확인 시각을 표시한다.

행동: 민감정보 없는 보고 미리보기, 오류 설명 보기, 고정 수신자에 한 번 재시도, 발신 연결 상태 확인. 수신자 자유 입력·신고 원문 첨부·이미지 첨부는 없다. 발신 미설정이면 ‘미연결’ 배지를 보이고 화면용 보고는 정상 생성한다.

E. 감사 기록

시간, 역할/담당자, 사건, action, 전후 revision, 범위 hash, 명시 확인 시각, 결과, 원본 감사 ID/동작 ID. 원문 사유는 허용된 상세 권한에서만 노출한다. 전역 목록은 안전한 reason code를 쓴다.

F. 비회원 긴급·권리 접수

상단 경고문으로 회원가입을 요구하지 않는다. 현재 메일 주소와 복사 가능한 요청 양식을 바로 노출한다. 추가 폼에는 일반문의/권리요청/긴급권리요청, 공개 URL, 설명, 연락처, 필요한 서명/진술, 접수용 개인정보 안내 버전만 둔다. 첨부파일·이미지 재업로드는 기본 제외한다.

원격 URL은 문자열과 허용된 공개 경로만 처리하고 서버가 임의 외부 URL을 fetch하지 않는다. 크기·빈도 제한, 중복 동작 ID, 봇 방어를 적용하되, 제한에 걸렸을 때도 기존 메일 경로를 명확히 안내한다. 연락처 검증 메일이나 운영자 triage를 기다리느라 이미 도착한 유효 요청의 시각을 늦추지 않는다.

폼은 접수 번호를 즉시 보여준다. 비회원 상태 조회를 붙일 경우 추측 불가능한 별도 receipt secret을 hash로 저장하고 최소 상태만 반환한다. 사건 번호만으로 원문·연락처·대상 소유자를 조회할 수 없다. 이메일 자동 접수 확인이 아직 미연결이면 화면에서 접수 결과를 보존할 수 있게 한다.

동작별 멱등성

Worker는 due row를 FOR UPDATE SKIP LOCKED로 최대 10개 claim한다. 짧은 lease를 발급하고 네트워크 timeout보다 긴 lease TTL을 사용한다. 실제 network 호출 전 dispatch_started_at을 기록한다. 완료 결과는 같은 lease_token/revision일 때만 반영한다. 만료된 lease는 재평가하되 dispatch가 시작되지 않았으면 다시 대기시키고, 외부 전송을 시도했는데 결과가 불명인 건은 UNKNOWN으로 분리한다. 한 worker의 batch·동시성·전체 실행시간은 실제 서버 제한 안으로 제한한다.

확실히 발송되지 않은 429/일시 5xx는 예를 들어 1분→5분→30분→2시간 간격과 jitter로, 최대 6시도 범위에서 다시 시도한다. 인증 만료/권한 오류는 즉시 DEAD로 전환하고 같은 인증으로 반복 발송하지 않는다. provider가 받아 간 후 응답만 유실된 경우에는 ‘정확히 한 번 전송’을 보장할 수 없다. stable Message-ID는 추적에 도움이 되지만 수신함 중복 제거 보장은 아니다. UNKNOWN은 운영자에게 중복 가능성을 보이고 결과 확인 또는 한 번의 재시도를 결정하게 한다.

ACCEPTED는 provider가 접수했다는 뜻이다. delivered 또는 ‘운영자가 읽음’으로 표시하지 않는다. 운영자가 대시보드에서 확인하면 별도의 사건/보고 확인 시각을 남긴다.

현재 작업에서 신규 자동 삭제·보존 만료 작업은 활성화하지 않는다. 법률·운영 문서에서 접수 본문, 연락처, 조치 감사, 메일 기술 로그 각각의 보존 목적·기간·예외를 확정한 뒤 별도 좁은 삭제 계획을 검토한다. 모든 자료를 동일 기간에 삭제하거나 무기한 보관하는 기본값은 두지 않는다.

공급자 연결안

•DB는 기존 Supabase를 쓴다. 현재 migration에 pg_cron이 등장한다. 새 운영 cron의 실제 설치·설정과 pg_net 가용성은 별도 확인해야 한다.

•신고 원문 테이블 전체를 webhook payload로 내보내지 않는다. 안전한 outbox enqueue 후 ID만으로 worker를 깨우는 async network 동작을 둔다. Supabase Database Webhooks는 pg_net 기반 async라는 공식 설명이 있으나 기본 webhook은 row 전체를 payload로 생성하므로 이 요구에는 그대로 붙이지 않는다.

•Vercel의 좁은 서버 endpoint가 due outbox를 claim하고 메일 어댑터를 호출한다. 재시도와 일일 생성은 Supabase cron의 5분 간격 짧은 SQL 작업 하나로 통합할 수 있다. 빈 큐이면 외부 HTTP 호출을 하지 않는다. 긴 작업·전체 테이블 스캔을 돌리지 않는다.

•현재 Gmail 주소에 보내는 관리자 보고의 발신 후보는 Gmail API의 gmail.send 범위만 쓰는 별도 OAuth 승인이다. 실제 발신 계정/승인·refresh 동작·운영 상태는 아직 확인되지 않았다. 앱 로그인에 쓰는 Google OAuth 토큰을 임의로 재사용하지 않는다. 연락함 읽기 권한은 관리자 보고 발신을 위해 필요하지 않다.

•메일 어댑터는 먼저 fake transport로 완성하고, 승인된 발신 계정과 고정 수신자를 마지막에 연결한다. 새 유료 발신 서비스나 앱 비밀번호를 가정해서 진행하지 않는다. 발신 미연결 상태에서도 대시보드와 보고 미리보기는 동작해야 한다.

경보가 너무 많이 오지 않게 하는 규칙

같은 사건·같은 원인의 경보는 하나의 사건으로 합친다. 확인 전 P0의 반복 알림은 예를 들어 4시간 간격, 심각도 상승·법정 기한 단계 진입은 즉시 새 event로 만들 수 있다. 일반 quota 경보는 임계 진입과 복구 시점에 알리고 매 점검마다 같은 메일을 보내지 않는다. 원시 신고 접수 자체는 삭제하거나 묵살하지 않고, burst는 ‘긴급 신규 N건’으로 묶어 전송한다. rate limit은 운영자 메일 폭주 억제용이지 법률 요청의 처리 시계를 멈추는 장치가 아니다.

deadman: 실행되지 않은 작업을 어떻게 찾는가

실패한 실행과 실행 자체의 부재를 구분한다. job마다 예정시각, 허용 지연, 최근 시도, 최근 성공을 가진다. current weekly backup은 03시 예정에서 약 05시대에 끝난 인수 기록이 있으므로, 03:05에 바로 실패로 낙인찍는 기준은 부적절하다. 초기 예로 주간 backup의 ‘아직 미확인’ 유예를 07:00 KST까지 두고 이후 사람이 확인하게 하되 실제 운영 기록으로 조정한다.

1.GitHub의 기존 cleanup/backup/health 결과가 ops-heartbeat에 작은 결과를 남긴다. report body·backup content·Storage 경로·secret은 보내지 않는다.

2.Supabase cron은 기대한 GitHub heartbeat가 없으면 사건을 만든다. GitHub scheduler 전체가 멈춘 경우에도 이쪽 경로가 살아 있으면 감지할 수 있다.

3.GitHub의 기존 freshness workflow를 좁게 확장해 Supabase의 보고 생성/worker heartbeat를 확인한다. 실패 시 기존 GitHub 실패 알림을 이용하는 독립 경로를 둔다. 메일 worker 자체가 죽었다는 경보를 같은 worker 한 개에만 맡기지 않는다.

4.09:10에 해당 날짜의 일일보고 생성 여부, 09:30에 장기 미처리 여부를 구분해 검사한다. 지연 실행은 원래 window_key로 멱등 처리한다. 긴 중단 뒤에는 누락 기간을 기록한 최신 catch-up 한 통을 만들고 과거 매일보고 수십 통을 쏟지 않는다.

5.큐 0건, 최신 cron 실행 행, HTTP 200만으로 종단 전송 성공이라고 표시하지 않는다. 최근 생성·최근 worker claim·provider 접수·운영자 확인은 서로 다른 관측이다.

이 구조도 Supabase·Vercel·GitHub·수신 Gmail이 동시에 불능이 되면 통지를 보장하지 못한다. 현재 무료·1인 운영안에서는 정기적인 사람의 대시보드 확인과 기존 GitHub 실패 알림을 함께 사용한다. 독립 경보의 실제 수신 검사는 정확한 테스트 대상/시각/한 통을 정해 최종 연결 단계에서 한다.

11. 자원과 운영 부담의 계획 가정

아래는 공급자 청구액이나 실제 사용량이 아닌 초기 설계 예산이다.

•정상 보고: 일일 30통, 주간은 월요일 일일에 합침. 긴급·복구를 월 20~70통으로 가정하면 월 50~100통. 1통 10~20 KB의 텍스트 중심이면 메일 payload 약 0.5~2 MB/월이다.

•5분마다 짧은 SQL tick은 월 약 8,640회. 큐가 비어 있으면 Vercel/Gmail을 호출하지 않는 구조로 둔다. 실제 SQL 시간·cron 로그 크기는 설치 후 관측한다.

•새 운영 사건 월 100건, 사건당 이벤트 10건, event/outbox 평균 수 KB를 가정하면 새 운영 데이터는 월 수 MB 규모로 시작할 수 있다. 법적 요청 원문·연락처 보존, 인덱스, cron/provider 로그를 포함해 별도 실제 증가량을 확인해야 한다.

•대시보드는 30초 실시간 polling을 기본으로 하지 않는다. 페이지 진입·수동 갱신·작성 후 갱신, 열려 있을 때 낮은 빈도의 안전한 refresh로 충분하다. 사진 원본 전송으로 건강 상태를 검사하지 않는다.

•기존 무료 한도와 함께 관측한다. DB/서버/메일 공급자의 무료 사용이 영구 보장된다고 약속하지 않는다. 임계 접근 시 기능별 추가 사용을 검토하고 대용량 로그·첨부를 줄인다. 사용자 기록을 자동 삭제해 새 관리 기능의 공간을 확보하지 않는다.

•1인 운영 비용은 신규 사건의 수보다 판단·당사자 응답·재발 확인 시간이 좌우한다. 2주 동안 사건 수, 최초 확인까지 시간, 사건별 실제 처리 분수만 간단히 적어 운영 가능 규모를 결정한다. 아직 없는 지표를 실측처럼 그리지 않는다.

12. 의미 있는 최소 검사

단순 화면 문구를 복제하는 대형 신규 테스트보다 아래 위험을 직접 검증한다.

1.역할 분리: 익명/일반계정/서비스 운영자/콘텐츠 심사자/둘 다 보유 계정을 나눠 호출. service_admin만으로 신고 원문·공개 이미지 심사·사본 조치에 접근하지 못하고, moderator만으로 발신 설정이나 개인정보 문의 연락처에 접근하지 못한다.

2.세션 경계: 사건 상세·이미지 요청 중 계정 전환/로그아웃/역할 회수. 늦은 응답·기존 확인 상태가 새 계정에 남지 않는다.

3.동작 멱등성: 조치 직후 응답 유실, 같은 operation 재조회/재전송, 다른 내용 재사용, 다른 탭의 revision 변경. 조치·앱 notice·감사/outbox가 한 번만 생기고 충돌에 자동 재승인하지 않는다.

4.기한: 유효 요청 수신 후 늦은 triage, 보완 요청, UTC/KST 경계, 월요일 보고 중복, 여럿의 단계별 기한. 48시간은 실제 trigger 수신 시각부터이고 내부 목표 변경에 끌려가지 않는다.

5.동일 사본: 보드 둘에 같은 source, 서로 다른 source에서 알려진 exact hash 일치, 다른 사진, full/thumb, 미니홈과 보드 연결, preview/publish 동시성. 승인한 공개 집합만 차단하고 비공개 원본과 다른 사진은 자동 변경하지 않는다. 알려진 비공개 source가 미해결인데 법률상 사건을 전체 해결로 처리하지 않는다.

6.공개 차단 확인: 대상 페이지뿐 아니라 직접 full/thumb URL의 실제 정책 차단과 bytes 미반환. quota 429·timeout을 삭제 성공으로 세지 않는다. owner 철회 후 moderator RESTORE가 재게시를 만들지 않는다.

7.기존 흐름 연결: 구 /moderation/ RPC에서 한 조치도 새 사건·감사·보고 목록에 반영한다. 원본 CLOSED만으로 새 사건을 무조건 RESOLVED 처리하지 않는다.

8.비회원 접수: 로그인 없이 필수 서면요건 제출/원접수 보존/응답 유실 재시도/상태 조회 권한/너무 큰 입력/스크립트 문장/외부 URL. 접수 내용을 명령·HTML로 실행하지 않는다. email 인증 대기 때문에 접수시각을 늦추지 않는다.

9.메일: concurrent worker, lease 만료, 429, 인증 오류, provider 접수 뒤 timeout, 수동 재시도. ACCEPTED와 수신·열람을 구분하고 민감 원문·사진·토큰을 snapshot 검사한다.

10.미실행: GitHub heartbeat 부재, DB cron 부재, worker 정지, 일일 생성만 성공/발송 실패, 긴 중단 뒤 catch-up. 같은 경보 폭주 없이 누락을 보여준다.

11.관측 의미: cleanup 완료+용량 경보, 수동 OBSERVE_ONLY, queue=0+run 없음, current UTC usage=0+전일 미측정, 오래된 데이터. 녹색으로 과장하지 않는다.

12.좁은 화면·접근성: 모바일에서 기한·다음 행동과 확인버튼을 읽을 수 있고, 키보드로 선택/취소/확인을 할 수 있다. 색만으로 긴급도를 표현하지 않는다.

실환경 최종 검사는 합성 사건과 승인된 공개 테스트 사본, 관리자 수신자 한 명을 대상으로 좁게 수행한다. 실제 이용자 사진이나 실제 피해 접수 내용을 검증 데이터로 쓰지 않는다. 전체 기존 회귀를 매 변경마다 반복하지 않고, 공개 경계 변경에 필요한 기존 계약 검사와 신규 위험 검사를 실행한다.

13. 개발 일정과 승인 경계

가정: 기존 코드에 익숙한 개발자 1명, 하루 5~6시간 집중, 운영자 판단·발신 계정 승인은 하루 이내 응답, 새 유료 공급자/새 앱 프레임워크 없음. 아래는 집중 작업일이며 외부 승인 대기와 실제 관측 기간은 별도다.

전체 구현은 약 9–15 집중일로 잡는다. 요구한 사건 처리와 위에서 구체화한 공개 사본 경계를 포함한 추정이다. 법률 적용 판단 대기, 알려진 비공개 원본에 대한 추가 조치가 필요한 경우의 별도 범위 설계, 외부 승인과 실제 관측 기간은 이 합계 밖이다. 우선 읽기 콘솔·비회원 안내·수기 접수·화면용 일일보고만 연결한 첫 유용한 버전은 3–5 집중일에 만들 수 있다. 이것을 전체 자동 운영 또는 TIDA 동일 사본 처리 완료로 표기하면 안 된다. 기존에 열린 개인 사진 문제의 수정 기간과 전체 서비스 복구 검증은 이 새 운영콘솔 추정에 섞지 않는다.

기한이 급한 법적 요청 경로는 자동메일 완성을 기다리지 않고 명확한 메일 안내·수기 접수 기록·알려진 공개 대상 수동 조치 절차를 먼저 운영할 수 있다. 반복 복사·확인 실수를 줄이는 콘솔과 자동보고는 이어서 붙인다.

승인 전에 완성 가능한 것

정적 관리자 검토 화면, 문구·업무 규칙·API/스키마 후보, 합성 데이터, fake mail transport, 격리 테스트, 정확한 migration/배포 diff, 복귀 계획, 발신 한 통의 구체 내용과 대상. 이번 작업은 그중 설계/정적 검토물과 작은 라벨 패치까지 준비했다.

최종 연결에 필요한 구체 승인

•검토된 exact commit과 migration을 어떤 Supabase/Vercel 환경에 반영할지.

•기존 운영자의 어느 업무 권한을 신규 접수/기한 RPC에 줄지. 임의로 새 운영자 계정을 만들지 않는다.

•승인된 발신 계정의 gmail.send 인증 경로와 고정 수신자 godburgundy@gmail.com, 관리자 테스트 메일 한 통.

•정확한 cron 정의와 허용 지연, 기존 GitHub freshness 변경, 제한된 누락/실패 수신 검사.

•동일 사본 조치의 구체 대상·범위·복구 조건. 테스트 사본과 운영 사본을 섞지 않는다.

보고 생성·전송이 불안정하면 우선 새 sender/cron만 비활성화할 수 있어야 한다. 접수 사건·기한·앱 알림·감사 기록은 그대로 남고 수동 확인은 계속된다. 권리 조치를 되돌리는 행위는 배포 rollback과 분리한다. 롤백만으로 owner가 철회한 게시물이 다시 공개되면 안 된다.
