## 1. 핵심 판정

**현재는 기능이 없는 것이 아니라, 작품을 진열하는 개인 컬렉션과 이미 공개한 기억을 다시 조립하는 미니홈이 서로 다른 제품처럼 구성되어 있다. 사용자의 목표는 하나의 컬렉션을 내가 편집하고 다른 사람은 허용된 부분을 보는 구조다.**

교정할 것은 세 가지다.

1. **제품의 관계:** 컬렉션이 미니홈이고, 그 안에 작품 선반과 이미지 보드라는 두 종류의 묶음이 있다.
2. **공개 자료의 계약:** 기존 Memory 공개 기능을 살리되, Memory가 없어도 작품 선반을 공개 전시에 넣을 수 있어야 한다.
3. **화면의 역할:** 갤러리·편집·공개 설정에 각기 적합한 공간을 배정한다. 흰색·얇은 선·작은 글씨만 일괄 적용하는 것으로 끝내지 않는다.

기존의 별도 메뉴 유지 권고는 이번 사용자 설명에 맞게 수정해야 한다. 그러나 개인 원본과 공개 읽기의 보안 경계를 합치는 것은 아니다. **사용자가 이해하는 공간은 하나, 데이터 권한과 공개 산출물은 분리**한다.

## 5. 현재와 목표의 차이

### 현재

```text
컬렉션 /                 내 작품 선반(titleKeys)
보드 /boards/            Memory 묶음(boardCards)
미니홈 /minihome/        이미 게시한 publication을 다시 선택·소개·정렬
방문자 /public/...       게시된 자료 읽기
```

컬렉션에서 선택한 선반은 미니홈의 입력이 아니며, 미니홈은 별도 관리 폼에서 시작한다. 데스크톱 주요 메뉴는 컬렉션·작품·기억이고 보드는 더보기, 미니홈은 보드 쪽 링크를 거쳐 찾는다. 이는 단순 메뉴 누락과 **조립 대상 자체의 차이**가 함께 있는 상황이다.

### 목표

```text
내 컬렉션 (= 내 미니홈)
  ├─ 작품 선반 ‘오래 남은 작품’       작품 참조 모음 / 기존 선반
  ├─ 작품 선반 ‘이번 분기에 보는 것’   작품 참조 모음 / 기존 선반
  ├─ 이미지 보드 ‘비 오는 장면’       Memory 참조 모음 / 기존 Board
  └─ 이미지 보드 ‘표정 모음’          Memory 참조 모음 / 기존 Board

내가 볼 때: 전체 소유 자료 + 편집·공개 설정
남이 볼 때: 공개로 확정한 부분만 + 팔로우·신고·차단
```

작품은 ‘어떤 애니를 묶었는가’, 이미지 보드는 ‘어떤 기억들을 묶었는가’다. 두 종류를 하나의 탭 이름으로 뭉개거나 같은 저장 row로 바꿀 필요가 없다. 반대로 프로필에 서로 다른 서비스로 가는 버튼만 놓고 통합 완료로 처리해서도 안 된다.

표시명 제안:

| 한국어 | 영어 | 역할 |
|---|---|---|
| 컬렉션 | Collection | 내 미니홈이자 전시·관리 중심 |
| 작품 선반 | Title shelf | 작품들을 고르는 기존 선반; 사용자 설명상 작품 보드 |
| 이미지 보드 | Memory board | 여러 Memory의 주제별 모음 |
| 작품 | Titles | 저장 작품·기억 보유 작품의 전체 탐색과 상태 관리 |
| 기억 | Memories | 전체 Memory 원본 아카이브 |
| 컬렉션 편집 | Edit collection | 내 소개·묶음 배치 설정 |
| 공개 설정 | Sharing | 공개할 부분과 항목을 확인하고 게시 |
| 방문자 보기 | View public collection | 현재 게시된 결과 확인 |

최상위는 **컬렉션 / 작품 / 기억**을 유지한다. 컬렉션 안에 묶음 선택과 ‘+ 묶음 추가’를 항상 찾을 수 있게 둔다. 묶음 추가에서는 작품 선반/이미지 보드를 고른다. 보드와 미니홈을 주요 메뉴에 각각 더 넣는 방식으로 끝내지 않는다.

### URL의 최소 변경안 — 정확한 query 명칭은 제안

| 경로 | 목표 |
|---|---|
| `/` | 소유자 컬렉션; guest는 로컬 컬렉션 |
| `/?section=title:<기존 shelfId>` | 선택 작품 선반 |
| `/?section=memory:<기존 boardId>` | 선택 이미지 보드 |
| `/?panel=sharing` | 컬렉션 공개 설정 모드 |
| `/?panel=following` / `?panel=safety` | 기존 관계/안전 기능을 같은 공간의 보조 작업으로 |
| `/boards/?id=...` | 같은 boardId의 컬렉션 내부 보드로 호환 이동 |
| `/boards/` | 컬렉션의 이미지 보드 선택/목록으로 호환 이동 |
| `/minihome/` 및 `#following/#safety` | 같은 컬렉션의 대응 작업으로 호환 이동 |
| `/public/home/?id=...` | 기존 homeId 유지. 같은 컬렉션 디자인의 공개 읽기 |
| `/public/board/?id=...` | 기존 publicationId 공유 링크 유지. 컬렉션 소속 문맥 표시 |
| 공개 작품 선반 | 우선 공개 home의 section 식별자로 열람. 불필요한 별도 공유 엔진을 만들지 않음 |

호환 이동은 원본 ID를 재사용하고 replace로 뒤로가기 루프를 피한다. 외부 returnTo, 계정 토큰, 무한 중첩 경로는 거절한다. 기존 미니홈 ID를 새로 만들면 팔로우·신고 대상과 공유 주소가 끊길 수 있으므로 보존한다.

### 사용자 상태

- **비회원 로컬 소유자:** 내 선반/이미지 보드를 사용. 공개 요청 시 기존 가입·승격 절차로 연결하며 미저장 draft와 귀환 위치를 지킨다. 로그인만으로 자료 업로드·공개를 동의한 것으로 보지 않는다.
- **회원 소유자:** 같은 컬렉션에서 편집. 비공개·공개 중·변경 미게시·제한 상태를 알아볼 수 있게 표시한다.
- **익명 방문자:** 공개 DTO만 읽는다. 숨긴 묶음의 이름·썸네일·순서 빈칸·총 개수도 노출하지 않는다.
- **다른 회원:** 익명 열람 + 기존 팔로우/해제·신고·차단. 팔로우로 비공개 권한을 얻지 않는다.
- **관리자:** 기존 관리자 권한·감사·가림/복원을 사용. 일반 소유자 도구에 관리 권한을 섞지 않는다.

## 7. 재사용과 신규 계약의 정확한 경계

| 대상 | 재사용 | 필요한 변경 |
|---|---|---|
| 선반 | 기존 ID·이름·titleKeys·Title State sync | 통합 컬렉션에서 참조·표시, 공개 작품 선반 DTO |
| Memory 보드 | boardId·N:M membership·순서·원본·metadata sync | 컬렉션 내부에서 열고 만들고 담는 UI |
| 공개 이미지 | 원본/사본 분리·준비·승인·전달·철회·quota | 새 화면에 컨트롤러 연결; 공개 선반 뒤 미리보기의 범위 엄격 제한 |
| 공개 미니홈 | homeId·발행/철회·revision·정책 동의·팔로우 | 기존 publication만 가능한 entries를 작품 선반 포함으로 확장 |
| 공개 보드 | 기존 publication DTO 및 링크 | 디자인·소속 내비게이션 공통화 |
| 신고·차단·관리 | 기존 서버 명령·권한·감사·노출 필터 | 새 공개 선반을 기존 대상 처리에 포함하는 최소 연결 |
| 감상 기록 | 이미 이동된 신규 편집기·writer·동기화 | 통합 전후 접근·같은 데이터 회귀만 |

**새로 필요한 핵심은 ‘통합 배치 참조’와 ‘작품 선반의 공개 표현’이다.** 이를 UI 변경만이라고 축소해서도, 공개 시스템 전체 재작성이라고 부풀려서도 안 된다.

### 소스가 보여주는 제한

- `normalizeBookshelf()`는 `id/name/titleKeys`만 남긴다. 임의 `kind/boardId`를 끼워 넣으면 사라진다.
- `minihomeSnapshot()`은 `publicationId`와 Memory `publicationSnapshot`을 요구한다.
- SQL `private.build_memory_minihome()`은 이미 공개된 Memory publication을 읽으며, 선반 titleKeys를 공개하는 분기가 없다. 후속 migration에도 선반 branch는 확인되지 않았다.
- 선반은 최대20개, 기존 public home은 최대10 entries 등 기존 경계가 다르다. 통합하면서 초과 자료를 잘라 버리거나 제한을 몰래 무제한으로 바꾸지 않는다.

### 권장 논리 모델 — 신규 물리 schema 확정 아님

```text
Collection layout (owner별, versioned)
  sections[] = sectionId + kind(TITLE_SHELF | MEMORY_BOARD) + sourceId + position

TITLE_SHELF source    -> 기존 shelfId -> titleKeys
MEMORY_BOARD source  -> 기존 boardId -> 기존 memberships
profile editing      -> 기존 home owner selection과 공개 프로필
published projection -> 공개로 확정된 typed entries + 기존 homeId
```

이름·membership을 두 군데에 복사해 각각 수정하는 ‘두 번째 보드’를 만들지 않는다. source가 내용의 기준이고 layout은 참조·순서만 가진다. 선택되지 않은 개인 자료가 public DTO에 들어가는 형태의 owner bundle 재사용은 금지한다. **공통화는 시각 컴포넌트, 데이터 공급자는 owner/visitor를 분리**한다.

초기에는 두 종류와 한 단계 깊이만 지원한다. Are.na처럼 임의 채널 중첩·협업·무한 그래프·다형 파일 저장소까지 일반화하지 않는다.

## 8. 공개 작품 선반: 가장 주의할 부분

### 8.1 Memory 없는 작품도 진열할 수 있어야 한다

작품 선반은 작품 목록이므로 Memory가 0개인 작품도 유효하다. 기존 Memory 게시 형식에 맞추려고 표지 기반 Memory를 자동 생성하거나 가짜 cardId를 만들면 안 된다. 공식 표지 사용의 기존 승인과 카탈로그 참조를 재사용하되 **새 공개 title 항목**으로 직렬화한다.

최소 공개안은 작품명 + 검증된 작품 참조 + 승인된 표지 revision이다. 현재 평점·시청 상태·재시청·감상·캐릭터/태그는 자동 포함하지 않는다. 해당 정보 공개는 구체 필드 선택과 preview에 포함될 때만 확장한다. 초기에는 ‘작품만’으로 완성할 수 있다.

### 8.2 표지 뒤 겹친 기억을 자동 공개하지 않는다

내 컬렉션에서 작품 표지 뒤로 보이는 preview는 개인 Memory다. 선반 공개가 그 작품의 모든 이미지 공개를 뜻하지 않는다.

- 내 보기: 기존 개인 Memory 펼침 유지.
- 공개 보기: 공개 범위에 명시적으로 포함되어 현재도 허용되는 해당 작품 Memory만 표시.
- 공개할 Memory가 없으면 표지만 표시. 숨긴 Memory 개수·가짜 겹침을 만들지 않는다.
- 초기 title-shelf 공개는 표지-only로 제공 가능하나, 개인 선반의 전체 Memory를 보여준다고 안내하지 않는다. 별도 이미지를 전시하려면 기존 이미지 보드를 같은 컬렉션에 넣을 수 있다.

### 8.3 공개는 화면 모드가 아니라 서버 결과다

‘방문자 보기’는 현재 게시된 public read를 확인하는 동작이다. 개인 화면을 CSS로 숨긴 미리보기를 방문자 화면이라 부르지 않는다. 공개 설정 중의 미리보기에는 아직 게시 전이라고 표시한다.

사용자는 한 공간에서 설정하지만, 서버는 기존대로 source/version/selection/rights/policy/hash를 검사한다. source가 바뀌면 기존 PREVIEW_CHANGED류 계약으로 재확인한다. 사용자 선택 밖의 새 카드가 같은 작품에 추가됐다고 공개판에 자동 포함하지 않는다.

제거·철회·원본삭제를 구분한다.

| 행동 | 기대 영향 |
|---|---|
| 컬렉션에서 묶음 제외 | 배치 참조만 제거. 원본 작품·Memory·보드 보존 |
| 작품 선반에서 작품 제외 | 해당 선반 membership만 변경 |
| 이미지 보드에서 기억 제외 | 해당 membership만 변경 |
| 공개 전시에서 제외 후 적용 | 그 공개 위치에서 제거. 독립 공유 링크 존속 여부를 명시 |
| 미니홈 비공개 | home 공개 중단; 기존 독립 board 공개는 현재 계약 유지 |
| 보드 비공개 | 해당 publication과 home의 참조 표시가 철회 규칙에 맞게 사라짐 |
| 카드 전체 공개 철회 | 모든 공개 위치·이미지 URL에 기존 철회 적용 |
| 원본 삭제 | 별도의 삭제 확인 및 기존 삭제 fence 적용 |

## 9. 호환 전환에서 놓치기 쉬운 두 가지

### 9.1 기존 소개·선택을 다시 입력시키지 않기

현재 SQL `get_memory_minihome()`은 selection을 반환하지만, `minihomeStatus()` 및 controller state는 selection을 보존하지 않고 UI는 nickname/bio/entries를 빈 값으로 초기화한다. 합성 controller 실행에서도 이 필드가 최종 state에 없음을 확인했다. 실제 브라우저 전체 재현은 아니다.

통합 편집은 **현재 소유자 draft / 마지막 게시 상태 / 화면의 미저장 변경**을 구분해 복원해야 한다. 자료가 도착했을 때 사용자가 먼저 입력한 내용을 덮지 않는다. 복원했다고 동의 체크를 다시 자동 수락하지 않는다.

보드 공개 제목도 현재는 매번 빈 값으로 시작한다. 기존 게시 설정이 있으면 우선 복원하고, 최초는 개인 보드 제목을 ‘공개용 초안’으로 채우는 개선을 권장한다. private 설명·감상을 공개할 사실로 자동 확정하지 않는다.

### 9.2 간편 카드 공유의 내부 보드를 모두 선반으로 노출하지 않기

`simpleCardSharing.js`는 간편 공유를 위해 cardId에서 결정적인 boardId를 만들고 1카드 보드를 생성할 수 있다. 따라서 모든 기존 board를 무조건 컬렉션 선반으로 자동 진열하면, 사용자가 만든 묶음이 아니라 ‘공개 카드 한 장마다 보드 하나’가 쏟아질 수 있다.

기존에 명시적으로 미니홈에 전시한 항목은 반드시 보존한다. 그 밖의 기존 보드는 컬렉션에서 선택해 넣을 수 있게 하되 자동 공개하지 않는다. 간편공유용 board는 생성 근거와 기존 참조로 분류하고 **제목·카드 수만으로 자동 삭제/추정하지 않는다.** 사용자가 이미 편집하거나 전시한 1카드 보드는 정상적인 보드일 수 있다.

## 10. 첨부 화면 진단

캡처는 보드의 공개 선택 단계다. 보드 열람 화면 전체나 Are.na의 원래 레이아웃이 아니다.

| 캡처/소스에서 확인한 것 | 왜 맥락이 어색한가 | 권장 교정 |
|---|---|---|
| 제목·설명과 하단 행동이 매우 넓음 | 목록용 가용 폭을 짧은 입력·다음 버튼에도 동일 적용 | 공개 작업 전용 최대폭과 action 영역 |
| 작은 표지가 한 행에 하나씩, 오른쪽 큰 공백 | 비교해서 고르는 작업인데 행 높이만 누적 | 썸네일 선택 그리드/간결한 행과 선택 상태 |
| 선택 전에 카드 공개 관리가 반복 | 고르기와 전역 철회가 같은 위계 | 선택 화면은 포함/제외, 전체 철회는 카드 관리 상세 |
| 공개 제목이 빈 값 | 기존 보드 문맥을 유지하지 못하고 재작성처럼 보임 | 기존 공개 draft 복원 또는 개인 이름으로 초안 |
| 감상 원문은 보이지만 공개 포함 여부는 별도 | 소유자 참고와 방문자 결과가 헷갈릴 수 있음 | ‘내 기록 참고’와 실제 공개 미리보기 구분 |
| 스크롤 중 작업 제목·닫기 문맥이 안 보임 | 현재 무엇을 공유하는지 잊기 쉬움 | 상단 작업 제목/단계, 긴 경우 고정 하단 행동 |

**닫기 버튼이 없다고 단정하지 않는다.** `MemoryPublicationPanel` 헤더에는 실제 닫기와 폐기 확인이 있다. 스크린샷은 페이지 중간이므로 보이지 않는 것과 미구현을 구분한다.

### 직접 연결되는 스타일 구조

- `channel-service.css`는 전역 `--page-max: 2400px`를 사용한다.
- `MemoryBoardView`는 보드 내용 아래에 `MemoryPublicationPanel`을 붙인다.
- `memory-publication.css`는 selection 한 행을 작은 썸네일 + 나머지 폭으로 나누며 form fieldset은 grid다. submit의 별도 정렬 규칙이 없으면 grid 폭으로 늘어난다.
- `public-surface-design.css`는 publication·safety·review의 입력·버튼·본문에 광범위한 selector로 스타일을 적용한다.
- `arena-refinement.css`는 그 위에 후속 override를 얹는다.

이는 CSS 로드 실패라고 확정할 근거가 아니다. **레이아웃의 의미를 구분하기 전에 외형 규칙을 넓게 덮어쓴 구조**가 현재 화면의 설명에 더 잘 맞는다. 전역 CSS 파일 개수 자체가 결함이라는 뜻도 아니다.

## 11. Are.na에서 가져올 것과 가져오지 않을 것

Are.na 공식 설명에서 channel은 block과 다른 channel을 담는 모음이고, connection은 자료와 모음 사이의 연결을 표현한다. 참고할 부분은 **지금 보고 있는 대상, 그 안의 이미지, 관련 정보, 다른 모음으로 가는 길**이 명확한 구성이다.

- 가져올 것: 콘텐츠 중심 화면, 일관된 이미지 모음 규칙, 얇지만 의미 있는 영역 경계, 내용 가까이 붙는 메타데이터, 읽기/편집 조작 분리.
- 가져오지 않을 것: 모든 화면에 같은 넓은 폭, 의미 없이 작은 글씨, 모든 기능을 details 안에 숨기기, 설정 폼까지 갤러리로 취급하기, Are.na의 채널 중첩 기능까지 복제하기.

본 문서의 폭·간격·인터랙션 수치는 MOEMOA용 제안이지 Are.na 공식 지침이 아니다. 특정 레퍼런스 채널의 현재 픽셀 배치를 이번에 직접 관찰했다는 주장은 하지 않는다.

## 12. 화면별 목표와 동작

### A. 소유자 컬렉션

- 상단: 닉네임/간단 소개, 현재 공개 상태. ‘컬렉션 편집’, ‘공개 설정’, 공개 중일 때 ‘방문자 보기’.
- 바로 아래: 접히지 않는 묶음 선택(작품 선반/이미지 보드 유형 표시), ‘+ 묶음 추가’. 검색과 보기 설정은 내용 영역에 맞게 보조 배치.
- 작품 선반: 현재 poster grid, 같은 작품 기억 뒤 겹침, PC 옆/모바일 아래 펼침 유지.
- 이미지 보드: 기존 PrivateMemoryCardPreview/BoardCollectionGrid의 시각·자료 경로를 재사용. 제목만 나열하지 않는다.
- 범위별 수: 작품 선반에는 작품 수, 이미지 보드에는 Memory 수. 두 수를 합쳐 ‘작품 N개’로 표시하지 않는다.
- 첫 사용: 실제 자료 없음 / 자료는 있고 아직 묶음 없음 / 선택한 필터 결과 없음 / 로딩 실패를 구분.

### B. 내용 편집

- 작품 선반 이름·작품 선택: 기존 BookshelfEditor의 draft/적용/취소 재사용.
- 이미지 보드 이름·설명: 기존 저장·취소 계약 재사용.
- 이미지 보드 membership의 현재 즉시 저장과 배치 편집 draft를 분리한다. 이미 저장된 카드 제거가 전체 ‘취소’로 복원되는 척하지 않는다.
- 기존 묶음은 참조해 배치. ‘담기’는 같은 cardId의 membership을 만들며 새 Memory 복제0.
- 분류·캐릭터 수정은 원본 Memory 편집기의 역할. 이 화면에 또 하나의 태그 엔진을 만들지 않는다.

### C. 공개 설정 — 첨부 화면의 대체

보드 아래에 길게 이어 붙이지 말고 **선택한 컬렉션/묶음의 전용 작업 모드**로 열고 닫는다. 전체 신규 공유 엔진이 아니라 기존 controller를 사용하는 presentation 교체다.

PC 제안:

```text
컬렉션 / 공개 설정                                  [닫기]
현재 선택 · 공개 결과 확인

[제목/설명, 최대 약 560px]     [선택한 묶음의 시각적 미리보기]
[작품/이미지 선택 그리드]      [선택 N · 제외/준비 필요 요약]
[선택 항목의 세부 설정]

                        [취소] [공개 결과 확인]
```

- 작업 canvas 최대 약1120px, 설정 열320~400px + 콘텐츠 열, 간격24~32px부터 검토한다. 한쪽을 빈 공백으로 방치하지 않는다.
- 선택 타일은 이미지·작품명·선택 여부를 하나로 묶는다. 다수 같은 작품의 Memory는 썸네일/짧은 감상으로 식별한다.
- 공개 필드 설정은 선택한 항목의 보조 영역 하나에서 연다. 기본 note/date/태그 비포함을 명확히 보여준다.
- 이미지 준비가 필요한 카드만 해당 작업을 안내하고, 처리 결과를 tile 상태로 되돌린다. 선택/준비/공개 완료를 같은 상태로 표시하지 않는다.
- ‘전체 선택’은 사용자의 명시적 행동이며 준비되지 않은 항목과 제외 이유를 보이게 한다.
- 최종은 기존 서버 prepare 결과 + 실제 허용 이미지 표시 + 필수 고지/동의 + publish. 요약 미리보기만으로 이를 건너뛰지 않는다.

모바일 제안:

- 1열 작업 구조, 선택 그리드는 읽기 가능한 2열 또는 작은 썸네일 행.
- 짧은 제목·선택 수를 상단에, 취소/다음은 안전영역을 포함한 하단 행동 영역. 키보드로 입력을 가리지 않게 한다.
- 개별 공개 옵션은 선택한 카드에서 한 번에 하나만 펼친다. 전체 폼을 modal 안에 여러 겹 중첩하지 않는다.
- 터치 hit area44px를 제품 목표로 삼되 PC의 작은 보조 링크까지 일괄 큰 박스로 만들지 않는다.
- 닫기/뒤로가기/취소는 같은 draft 기준을 적용한다. 게시 결과가 불확실한 동안 ‘취소되어 미게시’라고 단정하지 않고 기존 operation 결과를 확인한다.

### D. 방문자 컬렉션

소유자 화면과 동일한 헤더/선반·보드 네비게이션/이미지 렌더링 체계를 쓰되, 입력은 public DTO다. 편집 도구 대신 팔로우·공유·신고가 있다. 공개되지 않은 묶음은 잠금 타일로 암시하지 않고 응답에서 제외한다.

작품명을 눌렀을 때 방문자 자신의 Title Hub를 연다면 ‘작품 정보/내 기록 보기’라고 구분한다. 작성자의 private Title Hub를 public 콘텐츠처럼 보여주지 않는다. 작성자의 감상은 공개로 포함된 내용만 읽는다.

### E. 기존 보조 화면

- 작품/Title Hub: 두 보기·상태·평점·재시청·감상 관리 유지. 새 전시의 저장 의미를 덧씌우지 않는다.
- Archive/Memory 상세: 기존 기록·태그·이미지 편집 유지. ‘이미지 보드에 담기’가 통합 컬렉션의 같은 보드에 연결되도록 한다.
- 데이터/도움말: 이미 정리한 작업별 메뉴 유지. 레이아웃 변경으로 backup 포맷·정책을 다시 만들지 않는다.
- 팔로우/알림: 컬렉션의 보조 작업으로 접근. 기본 전시 옆에 이의제기 폼을 다시 항상 펼치지 않는다.
- 관리자: 콘텐츠 유형이 추가될 때 식별/가림/통지 대상이 끊기지 않게 하고 기존 관리 화면을 별도 전면 개편하지 않는다.

## 13. 전체적인 디자인 교정 방법

새 전역 CSS 한 장을 더 얹는 대신, 바꾸는 화면의 레이아웃 책임을 명시한다.

| 역할 | 공간 규칙 |
|---|---|
| 이미지 탐색/진열 | 화면 폭을 활용하되 카드 크기와 개수에 따른 grid |
| 상세 읽기 | 시각 요소 + 근접 메타데이터. 작품/Memory 유형에 맞는 비율 |
| 작성/공개 설정 | 읽기 가능한 form 폭과 별도 선택/미리보기 영역 |
| 운영/오류 | 요약과 정확한 대상·조치. 콘텐츠 전시 화면처럼 만들지 않음 |

색·폰트·간격 token은 공통으로 쓰되, 모든 화면을 하나의 레이아웃으로 강제하지 않는다. `.memory-publication .btn` 같은 광범위 규칙보다 화면 역할별 class에 폭/배치를 둔다. 변경 대상의 충돌 규칙을 확인하고 의미가 중복된 override만 그 범위에서 정리한다. 전체 CSS 청소는 선행조건이 아니다.

검수 대상은 파일 목록이 아니라 **사용자 장면**이다. 이번 대표 장면은: 작품 선반을 보는 소유자 / 이미지 보드를 보는 소유자 / 공개 대상을 고르는 중 / 방문자의 같은 컬렉션 / 긴 제목·다수 카드·준비 실패 상태. 이 장면을 같은 합성 자료로 PC와 모바일에서 비교한다.

기존 `arena-refinement.spec.ts`의 button count·width ratio·no-overflow 검사는 도움이 되지만 ‘작업 의미와 읽기 흐름’까지 보증하지 않는다. 핵심 질문은 ‘내가 뭘 보고 있고 무엇이 공개되는지 처음 온 사람이 설명할 수 있는가’다.

## 14. 실행 우선순위와 종료점

1. **관계 계약과 대표 장면 먼저 고정:** 이번 사용자 요청을 결정 로그에 반영하고, 동일한 합성 자료로 작품 선반1개+이미지 보드1개가 한 컬렉션에서 어떻게 보이는지 확인한다. 그림 시안만 끝내지 말고 실제 재사용 DTO로 구성한다.
2. **개인 컬렉션 통합:** 기존 선반/보드를 참조하는 소유자 화면과 저장/취소/복귀를 연결한다. 원본 마이그레이션 없이 시작한다.
3. **작품 선반의 공개 표현과 공통 visitor:** additive 계약을 추가하고 기존 Memory publication/homeId/관계를 연결한다. 이 부분은 새 서버 계약이므로 변경된 경계만 검증한다.
4. **공개 설정·호환 링크·잔여 레이아웃 마감:** 대표 장면이 안정된 뒤 같은 원칙을 필요한 화면에 적용한다. 기존 경로 유지 후 안전한 전환.
5. **영향 검증·정확 후보 승인:** 계약·시각·실사용 흐름을 구분해 보고하고 종료한다.

위 번호는 전달 문서의 설명 순서이지 새로운 release M/W 단계가 아니다. **W18을 사용자 흐름 담당으로, W07/W09/W10/W11을 바뀐 공개 계약 담당으로 연결**한다. W12/W13 관계·호환, W06 동기화, W14 신고/관리, W19/W20 검증·배포는 영향 범위만.

최종 완료 문장:

> 소유자가 자기 컬렉션 안에서 작품 선반과 이미지 보드를 구성하고, 선택한 범위를 같은 모습의 공개 컬렉션으로 보여준다. 방문자는 두 종류를 구경하고 팔로우할 수 있으며, 철회하면 모든 해당 경로에서 제외되고 원본은 보존된다.

‘메뉴에 미니홈 링크 추가’만으로 완료하지 않는다. ‘작품 선반을 공개하려면 Memory부터 만들어야 함’도 완료가 아니다. 반대로 취향 분석·여러 실험 레이아웃·새 홈·결제까지 넣지 않는다.

## 15. 남은 질문을 최소화하는 권장 기본값

- 공개 작품 선반: 먼저 작품명+표지만. 평점·상태·개인 감상은 별도 명시 필드로 후속 확장 가능.
- 게시 갱신: 내 편집 저장과 공개 적용을 분리하고, ‘변경 미게시’를 표시. 자동 공개로 변경하지 않는다.
- 화면 이름: 컬렉션 유지. 미니홈은 설명 또는 외부 공유 맥락에서 사용.
- 기존 데이터: 전부 보존. 기존 공개 전시는 현재 노출 상태를 유지하고 배치 초안만 제안한다.

사용자가 이 기본값을 바꾸는 경우만 해당 차이를 결정 로그에 남긴다. 이미 말한 컬렉션=미니홈 관계, 무료/Web 우선, 권리·철회 경계를 다시 확인 질문으로 돌리지 않는다.
