# Part A. 제품 기준

## 1. 변하지 않아야 할 제품 원칙

### 1.1 한 문장 제품 정의

> MOEMOA는 애니를 본 뒤 기억하고 싶은 순간을 30~90초 안에 Memory Card로 남기고, 개인 Archive와 Board에 축적해 시간이 지난 뒤 다시 발견하는 서비스다.

### 1.2 핵심 사용자 문제

```text
인상적인 장면·감정은 남는다
  → 스크린샷·메모·트래커에 흩어진다
  → 무엇 때문에 저장했는지 잊는다
  → 나중에 다시 찾거나 당시의 나를 회상하기 어렵다
```

MOEMOA는 작품 목록 자체보다 **작품과 연결된 개인 기억의 맥락**을 보존한다.

### 1.3 핵심 객체

| 객체 | 역할 | 초기 공개 범위 |
| --- | --- | --- |
| **Anime** | 기억을 연결하는 작품 인덱스 | 공용 또는 개인 전용 |
| **Memory Card** | 장면·감정·문장·날짜 등 하나의 기억 단위 | Private 기본 |
| **Archive** | 사용자의 모든 카드를 축적·검색·재발견하는 공간 | Private |
| **Board** | 하나의 카드를 여러 주제·감정·시기 기준으로 다시 묶는 공간 | Private 기본 |
| **Image Asset** | 카드에 선택적으로 연결되는 사용자 이미지 | P0는 기기 로컬 우선 |
| **Saved Reference** | 다른 사용자의 공개 카드를 파일 복제 없이 참조 | 공유 단계 이후 |

### 1.4 제품 경험의 기준 흐름

```text
애니 시청 또는 기억 회상
  → 작품 검색 / 개인 작품 생성
  → 기억 신호 1개 이상 입력
  → Memory Card 저장
  → Archive에 자동 축적
  → 같은 작품·감정·과거 시점의 카드 재발견
  → 카드 2~3개 이후 Board 생성 제안
  → 권리와 운영 체계가 준비된 카드만 제한적으로 공유
```

### 1.5 하지 않을 것

- MyAnimeList·AniList의 대체재를 목표로 한 대형 목록·평점 서비스
- 작품 제목만 저장하면 끝나는 일반 트래커
- 공개 피드·팔로워·좋아요를 초기 핵심으로 하는 SNS
- 애니 장면 캡처나 타인 팬아트의 공개 업로드를 기본 허용하는 서비스
- 저작권 이미지가 없으면 성립하지 않는 카드 디자인
- 핵심 기록 도중 광고를 노출하는 수익 모델
- 리텐션을 확인하기 전 AI 요약·고급 통계·전 국가 현지화 개발

## 2. 핵심 가설과 최종 판단 질문

| ID | 가설 | 관찰 행동 | 초기 통과 기준 |
| --- | --- | --- | ---: |
| H-01 | 사용자는 첫 카드 이후 반복 기록한다 | 활성화 사용자 중 D7 내 두 번째 카드 | 30% 이상 |
| H-02 | 기록이 쌓이면 자발적으로 다시 본다 | D7 의미 행동 리텐션 | 25% 이상 |
| H-03 | 저작권 이미지 없이도 가치가 있다 | 기본 디자인과 이미지 카드의 D7 격차 | 상대 20% 이내 |
| H-04 | Board가 단순 분류가 아니라 재방문을 높인다 | 카드 3개 이상 사용자 중 Board 생성 및 이후 재방문 | 생성 35% 이상, 방향성 개선 확인 |
| H-05 | 카탈로그 부족이 기록을 막지 않는다 | 검색 실패 후 기록 포기 | 20% 미만 |

수치는 업계 표준이 아니라 초기 내부 게이트다. 표본이 작을 때는 수치만으로 확정하지 않고 사용자 인터뷰와 실제 기록 패턴을 함께 본다.

> **최종 판단 질문:** “첫 카드가 예뻤는가?”가 아니라, **“첫 카드가 개인 아카이브의 시작이 되었는가?”**

## 3. 핵심 사용자와 초기 시장

### 3.1 1차 사용자

- 18~34세 영어 사용 애니 팬
- 인상적인 장면을 스크린샷으로 저장한 경험이 있음
- 짧은 감정·감상·대사를 메모한 경험이 있음
- 기존 갤러리·메모·트래커에서 기록이 흩어지는 문제를 느낌
- 긴 공개 리뷰와 커뮤니티 활동에는 부담을 느낌
- 모바일에서 시청 직후 빠르게 남기기를 원함

### 3.2 비타깃

- 방영 정보·스트리밍 위치만 찾는 사용자
- 완주 수·평점·랭킹 경쟁이 주 동기인 사용자
- 장문의 공개 리뷰와 토론이 주 활동인 사용자
- 팬아트·스크린샷 공개 홍보 플랫폼을 원하는 사용자

### 3.3 국가별 역할

| 국가 | 초기 역할 | 언어 | 판단할 내용 |
| --- | --- | --- | --- |
| **필리핀** | 주 사용자 확보·메시지 검증 | 영어 | 모바일 활성화, 유입 비용, 반복 기록 |
| **싱가포르** | 소규모 품질·지불 의향 교차 검증 | 영어 | UX 기대 수준, 백업·테마·회고 반응 |
| **베트남** | 영어 베타 이후 1개국 현지화 후보 | 초기 미지원 | 현지어 카피·채널 적합성 |
| **태국** | 영어 베타 이후 1개국 현지화 후보 | 초기 미지원 | 현지어 카피·채널 적합성 |

필리핀과 싱가포르의 반복 사용이 확인되기 전에 베트남·태국을 동시에 번역·운영하지 않는다.

## 4. 범위 기준

### 4.1 P0 — Private Memory Archive 베타

- 한 작품에 여러 Memory Card
- `작품 + 기억 신호 1개 이상` 완료 규칙
- 작품 검색 실패 시 개인 작품 생성
- 기본 디자인·텍스트 카드
- 선택적 기기 로컬 이미지
- 앱 내부 빠른 입력과 갤러리 파일 선택
- Share Target은 기술 검증 결과에 따라 포함
- Archive 기본 필터와 규칙 기반 재발견
- Private Board N:M 구조와 카드 순서
- 로그인 없는 로컬 사용과 선택 동기화
- 내보내기·복원·삭제
- 제품 이벤트·오류·비용 모니터링
- 개인정보·이용약관·저작권 연락 창구

### 4.2 P1 — 리텐션과 제한적 공유

- 분기·연간 회고
- 감정 변화·다시 보고 싶은 기록
- 텍스트·서비스 기본 디자인 중심 Unlisted 공유
- 이미지 유형·출처·라이선스·공개 범위 저장
- 본인 원본 또는 명확한 라이선스 이미지의 제한적 공개
- 스포일러, 신고, 차단, 삭제, 이의제기
- 다른 사용자 카드의 원본 참조 저장

### 4.3 P2 — 핵심 가치 검증 이후

- 공개 Board 탐색
- 제한적 팔로우·구독
- Supporter Pack 또는 반복 비용 기능의 구독
- 현지화 1개국 실험
- 독자적 회고·에디토리얼 화면의 제한 광고

### 4.4 보류 또는 금지

- 공개 이미지 중심 무한 피드
- 애니 장면 캡처·타인 팬아트 공개 기본 허용
- 포인트·랭킹·스트릭 경쟁
- 전체 애니 역사 카탈로그 완성
- AI 감상 분석·요약
- 핵심 작성·저장·검색 화면 광고

# Part C. 실개발 계획

## 7. 개발 원칙과 작업 방식

### 7.1 현재 코드 기반 활용

현재 Astro·React·IndexedDB·localStorage·Supabase snapshot sync·PWA·JSON 백업 기반은 폐기하지 않는다. 새 제품 모델에 맞게 도메인과 화면을 단계적으로 교체한다.

### 7.2 `master` 중심 개발 시 안전장치

현재 저장소 운영 방식을 유지하되 미완성 기능이 즉시 사용자에게 노출되지 않도록 한다.

- 기능을 작은 단위로 구현하고 각 단위마다 빌드·테스트 후 push
- 미완성 화면과 데이터 경로는 feature flag 뒤에 둠
- 스키마 변경은 기존 데이터를 먼저 읽을 수 있는 하위 호환 방식으로 배포
- 파괴적 마이그레이션 전에 백업 픽스처와 복구 경로 확인
- 문서만 바뀐 커밋과 런타임 변경 커밋을 분리
- 출시 태그를 남겨 문제 발생 시 직전 안정 버전을 식별

### 7.3 공통 완료 정의

모든 기능은 다음 조건을 만족해야 완료로 본다.

- 사용자 흐름과 빈 상태·오류 상태가 함께 구현됨
- 모바일·데스크톱 핵심 레이아웃 확인
- 접근성 기본 동작 확인
- unit 또는 E2E 테스트가 핵심 회귀를 보호
- 분석 이벤트가 중복 없이 발생
- 민감한 원문 데이터가 로그·분석에 남지 않음
- 마이그레이션·백업·복원 영향 확인
- 기존 기능을 깨뜨리지 않고 빌드 성공

일정은 1인 개발, 기존 코드 활용, 범위 고정이라는 전제의 **작업 추정치**다. 기능 결정 지연·PWA Share Target 제약·이미지 백업 방식에 따라 달라진다.

**개발 항목**

- Share Target 기술 스파이크
- 이미지 Blob 저장·리사이즈·export bundle 기술 스파이크

### F1. 데이터·이미지 기반 교체

**목표:** AniList 런타임·외부 표지 이미지가 없어도 핵심 기록이 동작하게 한다.

**주요 구현**

1. 자체 `animeId`와 카탈로그 출처 스키마
2. `aliases.json` 3,998개 항목의 `legacy_unverified` 변환
3. 검색 공급자 인터페이스와 외부 공급자 kill switch
4. 개인 작품 생성·수정·중복 후보 처리
5. 제목·색상·패턴·타이포그래피 기반 기본 커버 생성
6. 다가오는 분기 작품을 입력·검수하는 CSV 또는 최소 관리자 도구
7. 기존 라이브러리 항목과 새 Anime·Memory Card 간 마이그레이션 경계

**테스트**

- 외부 API 응답 없음·차단·지연
- 외부 이미지 0건
- 동일 작품의 영어·일본어·한국어 별칭 검색
- 중복 개인 작품 생성
- 레거시 데이터 변환 전·후 수량과 참조 무결성
- 마이그레이션 재실행의 멱등성

**완료 기준 G2-1**

- 외부 API와 외부 이미지를 모두 끈 상태에서 작품 생성·검색·카드 연결 가능
- 기존 사용자 데이터를 잃지 않고 새 스키마로 읽을 수 있음
- 모든 공용 카탈로그 항목에 권리 상태가 존재

1. 작품 + 기억 신호 1개 완료 검증
2. 한 작품에 여러 카드 생성·수정·삭제
3. 최근 작품·최근 감정·마지막 스타일 빠른 재사용
4. 앱 내부 파일 선택과 기기 로컬 이미지 저장
5. 이미지 리사이즈·용량 제한·EXIF 제거
6. Share Target 가능 플랫폼의 진입 경로와 공통 fallback
7. Archive 최근·작품·날짜·감정 필터
8. 동일 작품의 이전 카드와 일정 기간 전 카드 재노출
9. 이미지 제거 후에도 깨지지 않는 기본 카드
10. 첫·두 번째·세 번째 카드 이벤트

**저장 원칙**

- 외부 URL을 이미지 원본처럼 저장하지 않는다.
- 임시 object URL을 영구 데이터로 저장하지 않는다.
- 로컬 이미지는 IndexedDB Blob으로 저장하고 화면에서 필요할 때 표시 URL을 만든다.
- snapshot sync에서 이미지가 제외되면 카드에 `local_image_unavailable_on_this_device` 상태를 표시한다.
- 카드 삭제 시 연결된 원본·리사이즈 파일 삭제가 함께 검증되어야 한다.

**테스트**

- 제목만 입력한 카드 저장 차단
- 기억 신호 각 1개만으로 저장 가능
- 같은 작품 카드 여러 개 생성
- 이미지 허용·비허용 형식과 최대 용량
- 저장 공간 부족·권한 거부·파일 손상
- 오프라인 작성 후 재접속
- 카드 삭제·복원·마이그레이션
- 360px 모바일 레이아웃과 한 손 조작

**완료 기준 G2-2**

- 테스트 사용자 첫 카드 중앙 완료 시간 90초 이하
- 첫 카드 저장 성공률 99% 이상인 내부 테스트 세션
- 이미지가 없어도 전체 작성·Archive 흐름 완결
- 분석 이벤트가 실제 저장 성공 후 한 번만 발생

### F3. Private Board·재발견

**목표:** 카드 축적을 개인적 분류와 재방문의 이유로 바꾼다.

**주요 구현**

- `Board`, `BoardCard` N:M 관계
- Board 제목·설명·Private 공개 범위·순서
- 카드의 여러 Board 추가·제거

**테스트**

## 11. 지표 정의

### 11.1 핵심 퍼널

```text
landing_view
  → card_creation_started
  → title_selected 또는 private_title_created
  → first_memory_card_saved
  → second_memory_card_saved
  → archive_revisited / previous_card_opened
  → first_board_created / card_added_to_board
  → D7 meaningful action
  → D30 meaningful action
```

### 11.2 활성화

> 첫 방문 후 24시간 안에 작품을 선택 또는 생성하고, 기억 신호가 포함된 Memory Card를 1개 이상 저장한 사용자

제목만 저장, 샘플 카드 열람, 카드 작성 시작만 한 사용자는 활성화에 포함하지 않는다.

### 11.3 의미 행동

다음 중 하나 이상을 수행한 경우다.

- 새 Memory Card 작성
- 과거 카드 열람
- 카드의 Board 추가·제거·정렬
- 회고 화면 열람
- 다시 보고 싶은 기록 확인

단순 방문, 자동 새로고침, 알림 클릭만으로는 의미 행동으로 보지 않는다.

## 16. 홍보 메시지

초기 메시지는 서비스 객체보다 사용자가 얻는 결과를 말한다.

1. **Save the anime moments you don’t want to forget.**
2. **Your private anime memory journal.**
3. **Not just what you watched. What stayed with you.**

광고·랜딩·온보딩의 메시지가 서로 달라지지 않게 같은 문장과 같은 제품 장면을 사용한다.

## 17. 홍보 단계

### P-MKT 0. 개발 전 수요 탐색

- 기록 행동 사용자 15~20명 인터뷰
- 클릭만 받는 랜딩이 아니라 카드 완성형 프로토타입 테스트
- 3개 메시지의 이해도·완료율 비교
- 애니 커뮤니티에서는 운영자 허가 후 인터뷰 대상 모집
- 광고비를 쓰지 않고 문제·언어·첫 카드 흐름을 먼저 검증

### P-MKT 1. 내부·초대 베타 모집

- 개인 네트워크와 소규모 애니 커뮤니티에서 행동 기준으로 모집
- “새 애니 앱 테스트”가 아니라 “스크린샷·감상 기록을 어떻게 보관하는지 연구”로 설명
- 참여 보상은 경품보다 결과 공유·초기 기능 참여권 중심
- 가입자 숫자보다 2주 동안 카드 2개 이상 만들 의향이 있는 사용자를 우선

### P-MKT 2. 유기적 콘텐츠

권리 안전한 소재만 사용한다.

- 기본 디자인 카드가 쌓여 Archive가 되는 8~12초 화면 녹화
- 같은 작품에서 서로 다른 감정 카드가 생기는 예시
- 하나의 카드가 여러 Board에 연결되는 짧은 시연
- 이미지가 없어도 완성되는 카드 꾸미기 전·후
- “tracker vs memory archive” 차이를 설명하는 짧은 게시물
- 시즌 말 개인 회고 예시

실제 애니 포스터·장면·캐릭터·타인 팬아트를 광고 소재로 사용하지 않는다. 예시 데이터는 가상의 메모 또는 서비스가 직접 만든 그래픽을 사용하고 실제 사용자 기록처럼 보이게 하지 않는다.

### P-MKT 3. 유료 광고

**채널 우선순위**

1. Meta 통합 게재로 Facebook·Instagram·Reels 비교
2. TikTok·YouTube Shorts는 유기적 반응이 나온 소재부터 소액 재사용
3. 커뮤니티는 광고 게시보다 인터뷰·베타 모집 중심

**소재 구성**

- 동일한 8~12초 제품 데모 1개
- 메시지 문구 3종
- CTA 1개: 첫 Memory Card 만들어 보기
- 국가별로 동일 소재를 먼저 비교

초기 예산에서 형식·문구·국가를 지나치게 세분화하면 셀별 데이터가 부족해진다. 1차는 같은 데모와 문구 차이만 보고, 2차에서 우승 문구의 썸네일 또는 첫 장면만 비교한다.

## 18. 광고 성과 해석

| 결과 | 해석 | 다음 행동 |
| --- | --- | --- |
| CTR 낮음·첫 카드 낮음 | 메시지 또는 소재가 문제를 전달하지 못함 | 문구·첫 2초 수정 |
| CTR 높음·첫 카드 낮음 | 광고 약속과 랜딩·제품 경험 불일치 | 예산 중단, 퍼널 수정 |

| 첫 카드·D7 높음·비용 높음 | 제품 가치는 있으나 채널 효율 낮음 | 유기적·다른 게재 위치 비교 |
| 필리핀 양호·싱가포르 부진 | 가격이 아니라 품질·메시지 차이 가능 | 싱가포르 인터뷰와 UX 검토 |

```text
활성화 사용자당 비용
  → D7 두 번째 카드 사용자당 비용
  → D30 의미 행동 사용자당 비용
```

# 최종 실행 원칙

> **MOEMOA는 기능 수가 아니라 반복되는 개인 기억의 축적으로 검증한다.**  
> 이미지 없이도 첫 카드를 만들 수 있어야 하고, 첫 카드 뒤에 두 번째 카드와 자발적 재방문이 이어져야 한다.  
> 데이터 소유권·저장 신뢰·권리 안전을 먼저 확보한 뒤, Private → Unlisted → 제한 Public 순서로 확장한다.  
> 홍보비는 사용자를 사는 비용이 아니라 제품 가설을 검증하는 학습 예산으로 사용하며, 활성화와 D7가 확인되지 않으면 확대하지 않는다.
